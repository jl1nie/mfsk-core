# FST4 感度ベンチマーク — 環境セットアップ

FST4 の AWGN/フェージング SNR スイープ (`tests/fst4_sweep.rs`) を、
クリーンなチェックアウトからどの環境でも再現する手順。WSJT-X 本家の
`fst4sim` が生成する合成信号に対する SNR 対 recall を測定し、公式の
感度表と比較するためのハーネス（この整備のきっかけになった調査は
[#146](https://github.com/jl1nie/mfsk-core/issues/146) を参照）。

パイプライン全体は **WSJT-X の Fortran ソース → `fst4sim` バイナリ →
ディスク上の WAV コーパス → `cargo test --ignored` が WAV を読んで
recall 表を出力** という流れ。テスト実行時にネットワークは一切不要
（ビルドの一回きりのステップだけが WSJT-X ソースに触れる）。

## 1. 前提パッケージ

| 要件 | Ubuntu/Debian パッケージ | 用途 |
|---|---|---|
| `gfortran` | `gfortran` | `fst4sim.f90` と付随ライブラリのビルド |
| `gcc` | `build-essential` | `gran.c` のコンパイル |
| FFTW 単精度 | `libfftw3-dev` | `-lfftw3f` としてリンク |
| WSJT-X ソースツリー | — (下記参照) | `lib/fst4/*.f90` を提供 |

```sh
sudo apt-get install gfortran build-essential libfftw3-dev
```

**WSJT-X ソース。** `scripts/build_fst4sim.sh` が必要とするのは
`lib/` サブツリーのみ（Qt ビルドや `cmake` ステップは不要）。
`fst4/fst4sim.f90` シミュレータを含む WSJT-X チェックアウトであれば
何でもよく、本家ツリーでも構わない：

```sh
git clone https://github.com/jl1nie/WSJT-X.git ../WSJT-X
```

リポジトリルートの `CLAUDE.md` にあるテストフィクスチャパスの原則
どおり、このチェックアウトへの絶対パスを決してハードコードしない
こと — `build_fst4sim.sh` は明示的な引数として受け取り（デフォルトは
「リポジトリルートの兄弟ディレクトリとしての `../WSJT-X`」という
規約のみ）、クローン先が `/home/<you>/src/WSJT-X` でもどこでも同じ
手順で動く。

## 2. `fst4sim` をビルド

```sh
scripts/build_fst4sim.sh [/path/to/WSJT-X] [out-dir]
# デフォルト: WSJT-X-dir = ../WSJT-X（本リポジトリの兄弟）, out-dir = target/fst4sim/
```

`target/fst4sim/fst4sim` が生成される。これは合成専用のネイティブ
バイナリ（SDR/オーディオ I/O なし）— 300 秒の FST4-300 トライアル
1本を生成しても 1 秒未満なので、遅いのは*ビルド*の方だけ（約14
コンパイル単位、数秒程度）。

ビルドの動作確認：

```sh
target/fst4sim/fst4sim "CQ JL1NIE PM95" 60 1500 0.0 0.0 0.0 1 -20 F
ls 000000_*.wav   # -20 dB の 60 秒 AWGN トライアル1本
```

## 3. WAV コーパスの生成

用途に応じて2つの生成スクリプトがある：

- **`scripts/gen_fst4_sim_wavs.sh`** — サブモードごとに固定 SNR
  (-5 dB) のクリーンな AWGN ファイルを1本ずつ。
  `MFSK_FST4_SIM_ASSETS_DIR` を使う単一フレームデコードテスト用の
  軽量なスモークテスト・コーパス。
- **`scripts/gen_fst4_sweep_wavs.sh`** — 感度スイープ本体：全サブ
  モード（FST4-15/30/60/120/300）× 4つのチャネル条件（`awgn`,
  `ccir_good`, `ccir_moderate`, `ccir_poor`）× モードごとの SNR
  グリッド × `TRIALS` 回の繰り返し。これが `tests/fst4_sweep.rs` が
  読み込む対象。

```sh
scripts/gen_fst4_sweep_wavs.sh [fst4sim-path] [out-dir]
# デフォルト: fst4sim-path = target/fst4sim/fst4sim
#           out-dir      = embedded-poc/assets/fst4_sweep/
```

このスクリプトは**冪等・差分実行**——既に存在するファイルはスキップ
するので、SNR グリッドを広げたり `TRIALS` を増やして再実行しても、
コーパス全体を作り直すのではなく不足分だけを追加生成する。

### SNR グリッドの調整 — 測定の打ち切り (censoring) を避ける

スクリプト内の `MODE_SNRS` が、モードごとに生成する SNR ポイントの
一覧を指定する。**このグリッドはそのモードの公式 WSJT-X 閾値より
最低でも 1〜2 dB 深いところまで伸ばす必要がある** ——さもないと、
本当の 50% recall crossing をそもそも観測できない。生成した中で
一番弱いポイントでも安定してデコードできてしまっていたら、スイープ
から読み取った「感度」はグリッドがたまたま止まった場所のアーティ
ファクトであって、デコーダの実際の限界ではない（#146 では、まさに
このミスが後半3つの遅いサブモードで 3〜5 dB の見せかけの「ギャップ」
を生んでいた）。公式閾値は `mfsk-core/src/fst4/mod.rs` の doc-comment
に既に記載されているので、それと突き合わせること：

| モード | WSJT-X 閾値（AWGN, dB） |
|---|---|
| FST4-15  | -20.7 |
| FST4-30  | -24.2 |
| FST4-60A | -28.1 |
| FST4-120 | -31.3 |
| FST4-300 | -35.3 |

`TRIALS` は crossing 付近の分解能を決める——10 トライアルでは recall
が 10% 刻みでしか解像できず、50% ポイントを自信を持って特定するには
粗すぎる。本格的なスイープでは 20 以上をデフォルトにするのが妥当。

## 4. スイープの実行

```sh
MFSK_FST4_SWEEP_DIR=embedded-poc/assets/fst4_sweep \
  cargo test --test fst4_sweep --release \
  --features fst4,fft-rustfft,parallel \
  -- --ignored --nocapture
```

- `--release` は重要——スイープはモードごとに数百本の WAV に対して
  coarse-sync を回すため、デバッグビルドでは実用にならないほど遅い。
- `--features parallel` で `rayon` 並列化された coarse-sync
  fi-loop（#139）が有効になり、実行時間が大幅に短縮される——特に
  周波数ビン数が多い長周期モードで効果が大きい。
- 出力は単純な recall 表（モード × チャネル × SNR セルごとの
  decode数 / trial数）——pass/fail のアサーションはない。これは
  回帰ゲートではなく計測ツール。
- `MFSK_FST4_SWEEP_DIR` を未設定にすると
  `<repo>/embedded-poc/assets/fst4_sweep`（`CARGO_MANIFEST_DIR` 相対）
  がデフォルトになるので、別の場所で生成したコーパスを使うときだけ
  明示的に指定すればよい。

## 5. 結果の読み方

各モードについて、recall がまだ約50%ある最も低い SNR を探す——それ
が上の公式閾値表と比較すべき実測閾値。ヘッドライン数値と並べて
確認すべき点：

- crossing の SNR は生成したグリッドの*内側*にあるか、それとも
  最弱ポイントに張り付いているか？ 張り付いている場合はまだ
  グリッドが浅すぎるので `MODE_SNRS` をさらに伸ばして再生成する
  （手順3は差分実行なので安価）。
- AWGN と3つの CCIR フェージング条件を別々に比較する——AWGN でも
  現れるギャップと、フェージング条件でだけ現れるギャップは、
  パイプライン上の異なる箇所を指している可能性が高い。
- 特定のパイプライン仮説（探索空間のサイジング、周波数リファイン
  の精度など）を検証したい場合、recall の数字だけから逆算するより
  `core/sync.rs::SyncDims`（`n_freq`、`jz`/`n_lag`、`df`）を直接
  追った方が速いことが多い——スイープは効果量を確認・測定する
  ためのものであって、パイプラインのどこにギャップの起点があるかを
  発見するためのものではない。

## 6. 直す前に診断する — 当てずっぽうでスイープを回さない

フルスイープが教えてくれるのは「ギャップがどれだけ大きいか」で
あって「パイプラインのどこに起因するか」ではない。もっともらしい
メカニズム（測定されたギャップと数値的に一致する式）を選んで、
それに対する修正を書いて、フルスイープを回して確認する、という
やり方は遅く不確実——数値の偶然の一致が、フルスイープの再実行
（それ自体で数十分かかる）が「効果がなかった」と教えてくれるまで、
実装の全サイクルを間違った方向に進めてしまうことがある。

信頼できる順序はこうなる：

1. **一度だけスイープを回して**、recall が部分的（例: 20回中2回）
   な特定の (モード, チャネル, SNR) セルを見つける——常に0/20か
   常に20/20のセルより、時々成功・時々失敗するセルの方が診断的に
   はるかに有用。
2. **そのセルから個別のトライアルWAVを数本選び**、使い捨ての
   `#[ignore]` テストでパイプラインの各ステージを直接呼び出す
   （`tests/fst4_sweep.rs` の `fst4_60_diag_weak_trial` がそのパター
   ン）——まず `engine::sync::coarse_sync` で正しい候補がそもそも
   見つかっているか、`sync_min` に対してどのスコアかを確認し、
   次にその候補を`engine::pipeline::process_candidate_basic`に直接
   渡して、coarse-sync・fine-refine・LLR・BP/OSDのどこで実際に
   失敗しているかを見る。
3. **失敗しているステージを特定できてから**コードを変更し、
   （次節の）フルグリッドではなく*絞り込んだ*サブセットで
   再検証する。

これはまさに #146 の調査でハマった実例そのもの——「coarse-syncは
スロットの25%しか積分していない」という理論が、測定された約2.6dB
のギャップと数値的にほぼ一致していた（`sqrt(4) = 3.01dB`）ため、
それに対する修正を実装して回帰テストは通過したが、フルスイープを
再実行すると結果はバイト単位で完全に同一だった——手順2の診断
（事後に実行）で、正しい候補はすべてのトライアルで既に見つかって
おり、閾値を十分上回っていたことが判明したから。本当の原因
（FST4がWSJT-X自身の8シンボル相関の深さではなく、FT8向けに較正
された`LLR_NSYM_MAX = 3`を暗黙に継承していたこと）は、失敗した
候補を`process_candidate_basic`に直接通してトレースすることで
初めて見つかった。

## 7. 修正の再検証 — フルグリッドを回し直さない

具体的な修正があり、事前のフルスイープからおおよその50%クロス
点が既にわかっている場合、数dB以下の動きを確認するために全5モード
×4チャネル×フルSNRグリッド×`TRIALS`回を回し直すのは時間の無駄
（フルグリッドの実行は数十分オーダーかかる）。修正が動かしうる
範囲に絞って再検証する：

- **チャネル**: フェージング耐性（イコライズ、ドップラー追従）を
  狙った修正でない限りAWGNのみでよい——CCIR条件を足しても、基礎
  感度の修正に対しては診断的価値より実行時間の方が増える。
- **SNR範囲**: *以前測定したクロス点*をまたぐ2〜3dB幅だけでよい
  （例: 旧クロス点が-25.3dBなら-27〜-23dBだけ確認する）——既に
  わかっている0%/100%の両側のプラトーまで再スイープする必要はない。
- **モード**: 修正がモード非依存（`LLR_NSYM_MAX`のような定数が
  5つのサブモード全部に同じように効く場合）なら、メカニズムの
  確認には1〜2モードで十分——同じコードパスの再確認に5モード
  全部は要らない。
- 新しい50%クロス点は以前と同じ方法（隣接するSNRポイント間の
  線形補間）で計算し、ゼロから導出し直すのではなく以前のクロス点
  と直接diffを取る。

## 8. FST4-60A のデコード速度 — OSD エスカレーション・ゲートの過剰発火、約 8.4× の改善 (2026-07-20)

FT4 の coarse-sync / 速度改善と同じ手法 (`~/.claude/plans/dapper-soaring-nest.md`)
による新規調査。`docs/notes/BENCHMARKS.md` の「Decode speed」表では、
FST4-60A が全プロトコル中で golden WAV のデコードが唯一最も遅かった
(60 秒スロットに対して 2.60 s)。FT4 とは異なり、ボトルネックは
coarse 候補の冗長性では**なかった**。

**プロファイル** (`fst4_60_diag_candidate_cost_split`、`tests/fst4_sweep.rs`、
新規): WSJT-X の FST4-60 golden WAV (`210115_0058.wav`) では、
`coarse_sync` が見つけた候補は 31 の異なる周波数にまたがる 50 個だけ
(1.6× — FT4 の 4.5× にはまったく及ばない) で、`coarse_sync` と
`fst4_sync_search` を合わせても 110 ms 未満だった。本当のコストは
`symbol_spectra` + LLR + BP + OSD で、50 候補すべての合計が **8054 ms**、
これに対して `decode_frame` の本番の実時間は 2278 ms だった。

**根本原因、WSJT-X のソース** (`lib/fst4_decode.f90`、`lib/fec/ldpc240_101`
相当) **と突き合わせて確認済み**: 2 つの要因が重なっている。

1. `Ldpc240_101::decode_soft` (`fec/ldpc240_101/mod.rs:148-197`) は、BP が
   失敗して OSD が要求されると OSD を**2 回**試す。1 回目は生のチャネル
   LLR に対して、2 回目は — WSJT-X の `decode240_101.f90` の `zsave`
   機構 (issue #146) に忠実に — BP の軟推定値の累積和に対して行う。
   どちらも実際に必要なもの (issue #146 で zsum 再試行による実際の recall
   向上を測定済み) なのでバグではないが、OSD を試みるたびにコストが
   倍になる。
2. `process_candidate_basic` の OSD エスカレーション・ゲート
   (`osd_attempt_min`/`osd_depth3_min`、`core/pipeline.rs`) は、
   FT4 (すでに `N_SYNC` でスケールした版があった、issue #72) を除く
   全プロトコルで `(12, 18)` にハードコードされていた — これは FT8 の
   `N_SYNC=21` に対して較正された値である。FST4 の `N_SYNC=40`
   (8 シンボルの Costas × 5 ブロック) では、`18` は FT8 自身の
   18/21=86% よりも*はるかに緩い*基準 (18/40=45%) になるため、実際の
   信号品質に関係なく、実在の候補のおよそ半数が OSD depth-3 の段へ
   エスカレートしていた。
   `fst4_60_diag_osd_escalation` (新規) が golden WAV でこれを直接測定
   した: 50 候補のうち 24 個が OSD depth-2/3 を試行し (成功は 1 個、
   合計 3.7 s)、2 個がさらに depth-4 までエスカレートした (成功は 0 個、
   合計 2.1 s) — 実際の信号がどちらの閾値でも余裕をもって見つかって
   いた WAV での話である。
   これが置き換えたコメントは、FST4 の depth エスカレーション・ゲートは
   「すでに個別に調整済み」(issue #146) と主張していた —
   その調整の記録を `docs/historical/CHANGELOG-0.6-0.7.md` で調べたが
   見つからなかった。issue #146 が調整したのは `bypass_osd_score_min` と
   AWGN 感度であって、`(12, 18)` の組には一度も手が入っておらず、
   最初から FT8 の継承のまま放置されていたように見える (FT4 の調査で
   何度も踏んだのと同種の、古いコメントの罠である)。

**最初の試み: FT4 とまったく同じスケーリング式を再利用する** — `P::ID == Ft4`
の `((12*N_SYNC+10)/21, (18*N_SYNC+10)/21)` を FST4 にも拡張する
(`N_SYNC=40` では `(23, 34)` になる)。golden WAV の `decode_frame` は
197 ms (約 11.5×) に下がり、recall は不変 (1/1) だった。**しかし、同一
コードでの統制 A/B** (pipeline.rs の変更を git-stash し、まったく同じ
`fst4_snr_sweep` の AWGN セルを再実行して、元に戻す) では実際の劣化が
見えた: 50% crossing が **-27.6 dB → -27.1 dB** (約 0.5 dB) に動いた —
これは `docs/historical/CHANGELOG-0.6-0.7.md` に記録された 0.7.2 の
ベースライン (`-27.62 dB`) と照合して確認したもので、修正前の再実行が
これをほぼ正確に再現した (`-27.625 dB`) ため、古いベースラインのせい
という説明は排除できる。一見同じに見える FT4 の修正 (nsync が決して
到達できない閾値を*引き上げる*だけで、純粋に得しかなかった) とは異なり、
FST4 の `nsync` は、回収可能な実在の信号の一部について実際に `[18, 34)`
の範囲にまたがる — これは「同じ式、逆向き」に実際の recall リスクが
伴うケースであり、測定の前に指摘していたとおりだった。

その後の候補ごとの診断 (`fst4_60_diag_osd_depth34_nsync_floor`。CRC-24 の
通過だけでなく、デコードされたメッセージを `GOLDEN_MSG` と照合する) は、
depth-3/4 の救済下限を直接見つけようとしたが、空振りに終わった
(crossing 付近の AWGN 領域で救済は 0 件) — 実際のスイープでの劣化とは
矛盾しており、この診断の候補選択が本番と完全には一致していないことを
意味する (既知のギャップとして残し、これ以上は追わなかった。本ファイルの
候補ごとの診断はコスト/件数のプロファイルには引き続き有用だが、
`ft4_diag_smax_calibration` が FT4 で果たしたような recall 下限の
較正に対して信頼できることは証明されていない)。代わりに、実際の
`fst4_snr_sweep` テストを直接手でスイープする方式に戻した — FT4_BENCHMARK.md
の section 6 が使ったのと同じフォールバックである。

**較正、実際の recall テストに対して**:

| `osd_attempt_min` | `osd_depth3_min` | AWGN 50% crossing |
|---:|---:|---:|
| 12 (変更なし) | 34 (完全にスケール) | ≈ -27.3 dB |
| 12 (変更なし) | 24 | ≈ -27.44 dB |
| 12 (変更なし) | **20** | ≈ -27.56 dB |

`osd_attempt_min` は最初から最後まで元の `12` のままとした (それだけを
上げたこと — 前段の中間ステップで行った — が、最初の試みの 0.5 dB の
損失の主因だった。閾値付近の実在の候補の大半は、常に depth-3 とは限らない
ものの、OSD を*何らかの形で*試す必要がある)。`osd_depth3_min = 20`
(元の `18` をわずかに上回るだけ) は、記録されたベースラインをノイズと
呼べる程度まで再現した: AWGN は -27.56 対 記録値 -27.62 dB で、4 チャネル
すべてでの再実行もほぼ完全に一致した —

| チャネル | 記録値 (修正前、CHANGELOG 0.7.2) | 実測値 (修正後、今回のパス) |
|---|---:|---:|
| AWGN | -27.62 dB | -27.56 dB |
| CCIR good | -25.78 dB | -25.78 dB |
| CCIR moderate | -25.43 dB | -25.43 dB |
| CCIR poor | -24.50 dB | -24.50 dB |

— 4 チャネル中 3 つは記録値とビット単位で一致し、AWGN も 0.06 dB 以内
(20 トライアルの標本ノイズの範囲に十分収まる)。AWGN で FST4-120
(-30.71 対 記録値 -30.70 dB) と FST4-300 (-34.78 対 記録値 -34.78 dB、
完全一致) を抜き取り確認した — どちらのサブモードも同じ `N_SYNC=40` を
共有しており、同様に影響を受けないことを確認した。FST4-15/30 は
個別には再検証していない (時間制限のため。メカニズムは `N_SYNC` 起因で
5 つのサブモード全部に共通なので、これは妥当だが独立には確認されていない
外挿である — 将来 FST4-15/30 で劣化が現れたら見直すこと)。

**最終的な修正** (`core/pipeline.rs`): FST4 は専用の分岐を持つ —
`osd_attempt_min` は共有デフォルトの `12` のまま。`osd_depth3_min = 20`
は、実際のスイープで検証した手動較正値であり、`N_SYNC` 比の式から導いた
ものではない (その式が正しく再現したのは FT8/FT4 だけで、FST4 は直接の
較正が必要だった)。

**最終的な数値**: golden WAV の `decode_frame` の実時間は
**2278 ms → 272 ms (約 8.4×)**、recall は不変 (1/1、デコード総数も同じ 2 件)。
`llr+bp+osd` の合計コストは 8054 ms → 3262 ms。非 ignore の全スイート
(922 テスト) と `-D clippy::perf -D warnings` は終始グリーンだった。

教訓をはっきり言えば (section 7 が逆の方向から引き出したものと同じ):
以前に検証済みの修正と同一に見える修正 (同じ式、同じコードの形) でも、
基礎となる量が新しいプロトコルでは異なる振る舞いをするなら、異なる
リスクを伴いうる — FT4 の `N_SYNC` スケーリングが解放したのは死んだ
コードだけだったが、FST4 では一部の実在の信号が依存する*生きた*コードを
締めてしまった。出荷前にそれを捕まえたのは、(古いかもしれない以前の
ベースラインではなく) 現在のコードベースそのものに対する統制 A/B
だった。
## 9. Attribution ablation — 二つの救済メカニズムは重複するか (2026-08-17)

6-7節が扱ったのは、ギャップが*どこにあるか*の特定と、修正がそれを
動かしたことの*再検証*であった。本節が扱うのは、そのどちらにも答え
られない第三の問いである。失敗しているトライアルを救済するメカニズム
が**二つ**あるとき、それらは*同じ*トライアルを救うのか、それとも
*別の*トライアルを救うのか。

この区別が、embedded のエスカレーションラダーが両方の代価を払わな
ければならないか (issue #310)、安い方だけを持てばよいかを決める。
これは issue #306/#308/#311 から具体的に生じた問いである。FST4 の
OSD には救済候補経路が二つあった。WSJT-X の `i0±1` タイミングジッタ
再試行と、#198 以前の枝刈りなし組合せ OSD 探索への選択的フォール
バックである。

### カウントでは答えられない。答えられるのはトライアル単位の同一性だけ

それぞれ「5件中2件」を回復する二つのメカニズムは、**集計 recall の
数値からは区別できない**。次のいずれもありうる。

- **代替的 (substitutable)** — 同じ2トライアルであり、どちらか一方
  だけで全効果が得られる
- **加算的 (additive)** — それぞれ別の2トライアルであり、和集合は4
  で、どちらを外しても recall が下がる
- **相互作用的 (interacting)** — どちらも単独では働かず、組合せで
  のみ何かが救われる

したがってこの目的の ablation では、各構成が**どのトライアル**を
decode するかを集合として記録し、出力しなければならない。pass 数の
表だけでは不十分であり、「両メカニズムは同程度に効く」という要約
は積極的に誤解を招く。

### ノブ

- **OSD 探索**:
  `mfsk_core::fec::ldpc240_101::fst4_osd_diag_force_old(bool)` —
  `internal-testing` でゲートされた、プロセスグローバルな
  `AtomicBool`。`fst4_osd_decode` を旧来の枝刈りなし探索に強制する。
  `internal-testing` でないビルドでは常に `false` を返すため、リリース
  成果物には影響し得ない。**スレッドセーフではない**: `--test-threads=1`
  で実行すること。
- **タイミングオフセット**: 本番のエントリポイントには公開されて
  いない。罠2を参照。

### 罠1 — ハードコードしたトライアル番号は、実行に存在しない信号を指しうる

元の知見は、**1セルあたり100トライアル**のコーパスから
`[2, 15, 33, 45, 67]` というトライアルを名指ししていた。1セルあたり
20トライアルのコーパスにはトライアル33/45/67がそもそも存在しない
ため、それらの番号は黙って何も選択せず、5つの対象トライアルのうち
3つを飛ばした実行が、本物の 0/5 という結果に見えてしまう。

**トライアル集合は、存在するコーパスから導出し、見つかった件数と
使った集合の両方を出力すること。**

**真ではないこと (2026-09-08 訂正):** 本節はかつて、20トライアル生成
のトライアル2は100トライアル生成のものとは「*別の波形*」だと述べて
おり、`gen_fst4_sweep_wavs.sh` のヘッダも、再生成したセルの「トライ
アル番号はしたがって以後は別の信号を指す」と今も述べている。実測
したところ、`fst4sim` についてはどちらも誤りである。その出力は決定
的であり、実現値は要求されたトライアル数に依存しない。
`fst4_60_ccir_moderate_m26` を `TRIALS=2` と `TRIALS=100` で再生成
したところ、どちらも保存済みの20トライアルのファイルを**バイト単位で
完全に**再現した (md5、トライアル1-20)。同じ確認を四つのセル
(`ccir_moderate` m24/m25、`awgn` m27/m28) で行っても、80/80 が一致した。

したがって、既存の番号がすべて同じ信号を指し続けたまま、コーパスを
より大きい `TRIALS` で再生成して**拡張できる**。ここの m26 セルが、
最初の20トライアルで測ったものを何も無効にせずに 20 から 100 トライ
アルになったのは、そのためである。

なお成り立つのはより弱い主張であり、設計の拠り所にすべきはこちら
である: **番号は、それを生んだコーパスとセットでのみ意味を持つ。**
このマシンの `fst4sim` バイナリが、他所から引用された結果を生成した
ものと同じかどうかを確認するものは何もなく (sweep baseline がマシン
を記録している — `_meta.protocols.fst4` — のはまさにこのためである)、
20トライアルで存在するセルはトライアル67についての問いには答えられ
ない。`/home/ubuntu/...` のアセットパスをハードコードするのと同じ
類である (`CLAUDE.md` の "Test fixture paths" を参照)。問題はフィク
スチャの同一性ではなく、コーパスの状態である。

### 罠2 — 選択のベースラインに、検証対象のメカニズムが既に含まれていてはならない

トライアルを選ぶ最も安易な方法は、その不一致を最初に見つけた本番
経路の探索 (`decode_wav_fst4_60`、すなわち `DecodeRequest`) を再利用
することである。**これは今や循環している。** `DecodeRequest` の `osd`
フラグのデフォルトは `true` であり、#308 の `i0±1` 再試行はまさにその
フラグでゲートされている — つまり本番の "npre" アームには*既にタイ
ミング多様性が含まれている*。そのように選択したトライアルは、構成
上、タイミングが既に機会を与えられて失敗したものである。すると
タイミングアームは何も救えないことが保証され、この実行は「どちらの
メカニズムも効かない」という自信満々の結論を出すが、それは選択の
産物であって測定ではない。

これが特に効いてくるのは、検証対象のメカニズムが、元の知見と再測定
の間に*出荷された*ためである。そうなると、修正前のベースラインは
本番のエントリポイントにもう存在せず、ablation はそれを再構築しな
ければならない。

抜け道は二つある。優先順に:

1. **セル全体を全構成グリッドで測定し、集合は後から読み取る。**
   選択ステップがないので、バイアスのかかりようがない。
   `fst4_60_diag_npre_timing_substitutability_ablation` がこれを行って
   いる — 存在する全トライアルに対して、タイミング構成2 × OSD構成3。
2. グリッドが高価すぎる場合は、明示的に再構築したベースライン
   (単一の `i0` での npre) を使って選択する。現在の本番経路は決して
   使わないこと。

### `DecodeRequest` ではなく手組みのパイプラインを使う理由

本番のエントリポイントは**「タイミング多様性なしで OSD ありの npre」
を表現できない** — 両者は `depth.osd` ゲートで溶接されている。その
ため ablation は各ステージを直接呼び出す:

```
coarse_sync → fst4_sync_search → freq_shift_cd0
            → symbol_spectra / sync_quality → compute_llr → decode_soft
```

sync は**トライアルごとに一度**だけ走ってキャッシュされ、すべての
構成が同じ準備済み候補集合に対して評価される。したがって構成間の
差は、sync のジッタではなく OSD/タイミングの軸のみに帰せられる。

ここで間違えやすい点が二つある:

- `cd0` は `symbol_spectra` の前に `refined − coarse` だけ周波数
  シフトしなければならない (`freq_shift_cd0`)。これを省くと補正が
  ゼロになり、ablation が問題にしているまさに限界的な候補で `nsync`
  ゲートを人為的に失敗させてしまう。この一連の作業では、既にこれが
  原因で一度、非現実的に良すぎる測定が出ている。
- 成功は、既知の golden メッセージと照合して判定する。「何かが
  decode された」では判定しない。さもないと CRC の偽受理が救済として
  数えられてしまう。

**手組みの経路は本番より狭い** (候補は golden の ±5 Hz にフィルタ
され、sync は1パスのみで、SIC もない) ため、同じコーパスで
`DecodeRequest` より decode できるトライアルが少ないことがある。差を
メカニズムのせいにする前に、必ず同じファイルに対する
`fst4_60_diag_npre_osd_bug_hunt_ccir_moderate` と突き合わせること。

### 実行方法

```sh
cargo test -p mfsk-core --features full,internal-testing --release \
    --test fst4_sweep fst4_60_diag_npre_timing_substitutability_ablation \
    -- --ignored --nocapture --test-threads=1
```

20トライアルのセルで約6分 (6構成 × 20トライアルに、各1回の sync
パスを加えたもの)。テスト名でスコープする — 決して `-- --ignored` を
丸ごと実行しないこと。tier-C キャンペーン全体に拡大してしまう
(`CLAUDE.md` を参照)。

### 罠3 — セルはベースライン recall が部分的でなければならない

グリッドがメカニズムを切り分けられるのは、`npre @{0}` ベースライン
がゼロでも飽和でもないところだけである。0/n のセルでは、あらゆる
「救済」が無に対して測られることになり、既存のマージンを*広げる*
だけのメカニズムは見えない。n/n のセルでは、救うべき失敗がもう残って
いない。これは6節の規則であり、ここでは特に強く当てはまる。

この ablation の最初の実行は m26 CCIR-moderate を使った — #306 と
#308 の両方が名指しするセルである — が、このハーネスでは **0/20**
だった。`fst4_60_diag_npre_baseline_scan` が、使える帯域を安価に
(6構成ではなく1構成で) 特定する。2026-08-17、20トライアルコーパスで
測定:

| channel | m20 | m22 | m23 | m24 | m25 | m26 | m27 | m28 | m29 |
|---|---|---|---|---|---|---|---|---|---|
| AWGN | 20/20 | 20/20 | 20/20 | 20/20 | 20/20 | 19/20 | **12/20** | **3/20** | 0/20 |
| CCIR-moderate | 20/20 | 20/20 | 20/20 | **17/20** | **7/20** | 0/20 | 0/20 | 0/20 | 0/20 |

元の知見がこのハーネスでは使えないセルにあるという事実は、それ自体
が「手組みの経路は本番より狭い」の定量版である。本番は #308 のタイ
ミング再試行を備え、候補集合がより広く、±`FREQ_TOL_HZ` の事前フィル
タもないため、およそ 1–2 dB 深くまで届く。

### 罠4 — 単一メカニズム同士ではなく、組合せを和集合と比較する

最初の分類器は二つの単一メカニズムの集合を互いに比較するだけで、
*組合せ*をそれらの和集合と比較していなかった。そのため、単独の集合
が同一 (「代替的」) であるにもかかわらず、組合せは実際にはどちらか
一方より厳密に多くを救っているセルを「代替的」と分類してしまった
— #310 の答えを変える唯一の結果である。この種の 2×2 を手で書くなら、
最も重要な列は synergy 集合 (`both \ (timing ∪ fallback)`) である。
素朴な比較では見えないのも、この列だけである。

### 結果、2026-09-08 — n=100 での使える帯域 (4セル)

その下にある20トライアルでの読みが先に得られたもので、見つけた罠の
ために残してあるが、**大きさの引用には使うべきではない**。n=20 では
二つのセルで、どちらの単一メカニズムも全く何も救っていないように
見えたが、これはサンプルサイズによる人工物である。コーパスは、
`TRIALS=100` で再生成することで1セルあたり100トライアルに拡張した
(罠1を参照 — 既存のトライアルはバイト単位で同一に戻るので、以前に
測ったものは何も無効になっていない)。Apple M5、1セルあたり約15分。

絶対 recall、6構成すべて:

| cell | `npre @{0}` | `npre @{0,±1}` | `unpruned @{0}` | `unpruned @{0,±1}` | `npre→unpruned @{0}` | `npre→unpruned @{0,±1}` |
|---|---:|---:|---:|---:|---:|---:|
| CCIR-mod m24 | 61/100 | 69/100 | 68/100 | **77/100** | 68/100 | 77/100 |
| CCIR-mod m25 | 23/100 | 27/100 | 26/100 | **34/100** | 26/100 | 34/100 |
| AWGN m27 | 78/100 | 84/100 | 82/100 | **87/100** | 82/100 | 87/100 |
| AWGN m28 | 29/100 | 42/100 | 34/100 | **43/100** | 34/100 | 43/100 |

`npre @{0}` ベースラインに対する救済を、件数で:

| cell | baseline | timing alone | fallback alone | overlap | both | only-with-both | verdict |
|---|---:|---:|---:|---:|---:|---:|---|
| CCIR-mod m24 | 61/100 | 8 | 7 | 5 | 16 | **6** | **synergistic** |
| CCIR-mod m25 | 23/100 | 4 | 3 | 0 | 11 | **4** | **synergistic** |
| AWGN m27 | 78/100 | 6 | 4 | 3 | 9 | **2** | **synergistic** |
| AWGN m28 | 29/100 | 13 | 5 | 4 | 14 | 0 | partial overlap |

**4セル中3セルで、組合せはどちらのメカニズムも単独では救えない
トライアルを救う。** 20トライアルでの読みから変わった二つの判定
(m24 の partial → synergistic と、m25 の大きさ) が変わったのは、
n=20 では100あたり3-8トライアルの救済がそもそも見えなかったから
である。

小さいサンプルでは決められず、大きいサンプルが決める点が三つある:

- **両メカニズムとも単独で効く。** n=20 では、m25 は「どちらの
  メカニズムも単独では何も救わない」と読めた。n=100 では、タイミング
  は4件、unpruned フォールバックは3件を救い、両者の間の重複は
  *ゼロ*である。先の「単独では効かず、組合せだけが効く」という枠組み
  は、メカニズムではなく小サンプルのノイズであった。
- **どのセルでも、タイミングの方が強い単独のレバーである** (フォール
  バックの +7, +3, +4, +5 トライアルに対して +8, +4, +6, +13)。#310
  にとっては、ラダーが一つの段しか賄えないならそれがその段であり、
  AWGN m28 ではフォールバックの 2.6× の価値がある。
- **`npre→unpruned` フォールバックは、`unpruned` 単独と全く同じ**
  である。4セルすべて、両方のタイミング設定で — 件数が同じというだけ
  でなく、集合が同一のもの8組中8組である。`npre` を先に走らせて
  フォールバックしても、常に unpruned を走らせる場合に対して何も得
  られず、`npre` パスのコストが余計にかかるだけである。20トライアル
  での読みはこれを一つのセルで見て、「挙動としては同じもの」と呼んだ
  が、測定した全セルでそれが成り立つ。

そして、ラダーとは全く関係のない点がもう一つある。**`npre` が
`unpruned` の取りこぼしを救うことはない** — 「npre が unpruned の
取りこぼしに勝つ」集合は、4セルすべて、両タイミング設定で空である。
このコーパスでは、recall の面で枝刈り探索は枝刈りなし探索の厳密な
部分集合であり、したがって npre1/npre2 の価値は完全に速度である
(CoreS3 の候補ループで 1.25-1.5×、issue #198)。これは妥当なトレード
オフだが、「AWGN recall は変わらなかった」ではなく、トレードオフと
して述べるべきである。

メカニズムとして synergy は筋が通っている。枝刈りなし探索はより多く
のパターンを探索するが、渡された LLR が十分に良い場合にしか役に立た
ず、別の `i0` こそがより良い LLR を生む。両方の条件が同時に成り立つ
必要がある — このため、ベースラインに余地がある三つのセルでは synergy
集合が空でなく、タイミング単独で14件中13件を既に担っている AWGN m28
では空になる。

**どちらのメカニズムの救済集合も、もう一方を含まない**。n=100 では
どのセルでも — どのセルにも、タイミングだけが救うトライアル*と*、
フォールバックだけが救うトライアルの両方がある (m24 は 3 と 2、m25
は 4 と 3、m27 は 3 と 1、m28 は 9 と 1)。20トライアルでの読みは二つ
のセルで包含関係を見て、そこからエスカレーション順序を推論したが、
n=100 では導出すべき順序は存在しない。

**#310 について**: ラダーは、トライアルを失わずに一つのメカニズムに
削減することはできない — ただし今は、値付けできる大きさがある。
unpruned フォールバックを外してタイミングを残すと、4セルで100あたり
8, 7, 3, 1 トライアルを失う。タイミングを外してフォールバックを残す
と 9, 8, 5, 9 を失う。実ハードウェアで測った、フルのタイミング多様性
のコスト 2.5–3× に対して、これは意図的に行うべきトレードであり、
残すべき安い方の段はタイミングである。

| `npre→unpruned @{0}` | 0/20 | — |
| `npre→unpruned @{0,+1,-1}` | 3/20 | 1, 4, 17 |

**判定: 相互作用的であり、代替的でも独立な加算的でもない。** どちらの
メカニズムも単独では何も救わない — タイミング多様性は `npre` に対して
何もせず、枝刈りなし探索は単一の `i0` では何もしない。組合せだけが
decode し、フォールバック構成のヒットは単なる `unpruned + timing` と
*同一*であり、つまりこの三つのトライアルでは `npre` は何も寄与して
いない。

#310 にとってこれは、ラダーが二つのうち安い方を単純に選ぶことはで
きないことを意味する。このセルで救済となるのは組合せであるため、
`offsets = &[0]` を維持する embedded ビルドは、枝刈りなし OSD の
フォールバックを加えても何の利益も得られない。

*このセル*のすべてのトライアルは `osd_depth = 3` に達しており、した
がって `npre2` は全体を通して働いていた。これは一般化**されない**。
上記の使える帯域では、BP だけで decode するトライアル (`depth = 0`、
例: m24 のトライアル7と17) もあれば、`depth = 2` で止まるトライアル
(m28 のトライアル4と10) もある。`npre2` がそもそも関与するかどうか
はセルに依存するため、#311 が提起した npre1 対 npre2 の局在化の問い
に答えが出たのは最も深いセルについてだけであり、一般にではない。

### 注意事項 — 判断の拠り所になるため明記する

- **1セルあたり20トライアルで、救済件数は一桁。** 方向性を示す
  にとどまる。ここにあるものは本番のデフォルトを動かすべきでは
  なく、そのためには near-threshold スイープが必要で、コスト面には
  実ハードウェアが必要である。
- **判定はセルに依存するので、セルを明示して引用すること。** 4セル
  のうち二つは synergistic で二つはそうではない。この ablation を
  単一セルで実行すれば、どちらの結論も出せてしまう。帯域を報告する
  こと。
- **#308 固有の 2/5 のタイミングでの勝ちを再現するセルはない。**
  #308 はそれを100トライアル生成で測り、このコーパスに含まれない
  トライアル33/45/67を名指ししていた (罠1)。未解決であり、**ここで
  はテストできない**: `fst4sim` がインストールされておらず、100
  トライアル生成をこの環境では構築できないためである。そのセット
  でグリッドを走らせるまでは、これらの表を #308 と矛盾するものと
  読まないこと。
- サブモードは一つ (FST4-60) のみ、ターゲットメッセージも一つで、
  golden の周波数の ±`FREQ_TOL_HZ` への sniper 式の候補事前フィル
  タを使っている。
- **wall-clock は意図的に報告しない。** これは recall の帰属
  (attribution) である。コストの数値は Ryzen 9 機か実ハードウェアで
  測るべきものである — Apple のノート PC の AC/バッテリー状態は、
  ホストの wall-clock を約3×も振らせる (`BENCHMARKS.md` はまさに
  この理由でマシンを記録している)。

## 10. Sniper candidate cap — 絶対数ではなく保持率で (2026-08-17)

issue #312、#306 に対する VK3NV のフォローアップから。
`fst4_60_diag_sniper_gate_width_sweep` は、実際の FST4-60 golden
(`210115_0058.wav`、230 Hz 離れた既知の2信号: N5TM @ 1101 Hz、
K9KFR @ 1331 Hz) の上で、sniper 経路の探索幅**と** `max_cand` の
cap をスイープする。

```sh
cargo test -p mfsk-core --features full,internal-testing --release \
    --test fst4_sweep fst4_60_diag_sniper_gate_width_sweep \
    -- --ignored --nocapture
```

### `frac` 列が要点である理由

絶対値の cap は、幅をまたいで**比較できない**。実測:

| width | raw population | `max_cand = 50` is… |
|---|---:|---|
| ±250 Hz | 842 | top **6 %** |
| ±100 Hz | 332 | top **15 %** |
| ±50 Hz | 165 | top **30 %** |
| ±25 Hz | 85 | top **59 %** |

一つの定数が、保持ポリシーに 10× の幅を生む。これはまた、cap を固定
したまま窓を狭めると false survivor の数が*増える*理由でもある
(N5TM: ±250 から ±25 Hz で 21 → 29) — 狭い窓は、それ自身のより小さい
プールのはるかに大きな割合を保持するためである。これを「狭めると
悪化する」と読むのは、この列が防ぐために存在する罠である。

### 保持率を揃えると、窓を狭めれば false survivor は確かに減る

cap を揃えるのではなく、保持率 ~5 % で各セルを比較する:

| width | cap | frac | false survivors (N5TM / K9KFR) |
|---|---:|---:|---|
| ±250 Hz | 50 | 6 % | 21 / 18 |
| ±100 Hz | 16 | 5 % | 9 / 10 |
| ±50 Hz | 8 | 5 % | 5 / 6 |
| ±25 Hz | 4 | 5 % | 1 / 3 |

同じ保持ポリシーで false survivor はおよそ **20× 少なく**、両ターゲット
とも幅に対して単調である。~10 % の保持率でも同じ形になる。つまり
幅と cap は入れ替え可能なノブではない。幅は本当にノイズのプールを
縮め、cap を比較するのに適した軸は割合である。この証拠からは、幅
から導いた cap は正当化できるが、幅をまたいで固定した定数は正当化
できない。

### このスイープが答えられないことと、その理由

**golden の2信号はどちらも強く、それでも `max_cand = 4` まで下げた
すべての幅でターゲットは decode される。** 表のどこにも recall の崖
に達していないため、切り詰めが弱い decode を犠牲にし始めるのがどこ
かを特定できない — これはより厳しい cap が提起する問いのすべてで
ある。VK3NV はこのスイープを依頼したときにこのスコープの限界を指摘
していた。それは今も成り立つ。本番のデフォルトを動かす前に、
near-threshold の AWGN/CCIR スイープを走らせなければならない。

また、`decoded` は decode の*成功*を数えており、複数の候補が同じ信号
を decode する場合も含むため、recall の数値ではない。±100/±50/±25 Hz
では窓内に既知の信号が一つしかないので、そこでは構成上 `real ≤ 1`
であり、両方を含むのは ±250 Hz の行だけである。

### 監査: dedup で抑制された候補が cap を超えて再度受け入れられる

VK3NV の #312 フォローアップは、`engine/sync.rs` の到達可能な経路を
指摘した。dedup ループは負けた近接重複 (4 Hz / 40 ms) を `score = 0.0`
でマークするが、直後の `retain` は、スコアに関係なく `stage1_pass(fi)`
を満たすものを受け入れる。`stage1_norm` は FST4 でしか埋められない
ので、これは FST4 固有である。

`fst4_60_diag_dedup_zero_score_readmission` はこれを直接数える —
出力の `score` がちょうど `0.0` になるのはその dedup の代入からしか
ありえず、`SyncCandidate::score` は公開なので、ライブラリの変更は
不要だった。

**発生はするが、懸念が想定した場所ではない。** 二つの golden ター
ゲットと near-threshold スイープの二つのトライアルについて、4幅 x 6
cap にわたって測定:

| source | width | cap | capped | zeros | zeros in reserved near-hint group |
|---|---|---:|---:|---:|---:|
| golden / K9KFR | +/-250 Hz | 50 | 50 | 3 | 3 |
| golden / K9KFR | +/-100 Hz | 50 | 50 | 3 | 3 |
| golden / K9KFR | +/-50 Hz | 50 | 50 | 3 | 3 |
| golden / K9KFR | +/-25 Hz | 50 | 50 | 6 | 3 |

それ以外の行はすべてゼロである — **50 未満のすべての cap**、二つの
near-threshold スイープのトライアル、N5TM の全体を含む。

理由は、zero がグループ内の最後にソートされるため、低い cap はそれ
らが問題になる前に切り捨ててしまうからである。`reserved =
min(near.len(), cap.div_ceil(2))` は `near` の上位を*スコアで*取り、
ここでは `near` に常に少なくとも `reserved` 個の非ゼロ候補があった。

**したがって、この注意点は仮説とは逆の行に当たる。** 上の表の低い
cap の行は影響を受けず、11.2節の near-threshold recall の数値も同様
である。影響を受けるのは `max_cand = 50` — 本番のデフォルト — であり、
二つの golden 信号の一方では、**50スロット中3スロット (6 %) が既に重複
と分かっている候補に割り当てられ**、その三つはすべて予約済みの
near-hint グループ内にある。

**フォローアップ: 再度受け入れられた重複は、そもそも decode される
のか。** `fst4_60_diag_dedup_zero_score_recall_effect` が、本番の
`max_cand = 50` で、部分 recall の帯域にわたって、sniper 形状
(`freq_hint` あり) で、これに直接答える。二つの列がある。`coarse_sync`
が返したままの候補リストでの recall と、decode 作業の前に
`score == 0.0` のエントリを落としたときの recall — つまりゲートを
厳しくした場合にまさに起こることである。

| cell | n | zeros reaching the list | zeros that decoded | recall as-is | recall filtered |
|---|---:|---:|---:|---:|---:|
| CCIR-mod m24 | 20 | 1 | **0** | 18/20 | 18/20 |
| CCIR-mod m25 | 20 | 1 | **0** | 9/20 | 9/20 |
| AWGN m27 | 20 | 4 | **0** | 15/20 | 15/20 |
| AWGN m28 | 20 | 3 | **0** | 6/20 | 6/20 |

**再度受け入れられた重複は何も decode せず、それらをフィルタしても
どのセルの recall も変わらない。** この経路では、OR ゲートによる再
受け入れは何も生まないので、`retain` を `score >= sync_min &&
stage1_pass(fi)` に厳しくしても recall は失われず、重複が消費する
スロットが戻ってくる。

サンプルは小さくスコープも狭い — 80トライアルにわたるスコアゼロの
候補が9件、FST4-60 のみ、幅は一つ (+/-250 Hz)、cap も一つ、sniper
形状のみである。ゼロが予約スロットではなく最下位に並ぶ、広帯域の
`DecodeRequest` 形状 (`freq_hint` なし) も、上の表の3つのゼロが現れた
強信号 golden のケースも対象としていない。「決して decode されない」
は、ここでは裏付けられたにとどまり、一般に確立されたわけではない。

ここでは修正していない: これは既存の挙動の測定であり、`retain` が
`score >= sync_min && stage1_pass(fi)` を検査すべきか (あるいはゼロ
化されたエントリを明示的に除外すべきか) は、#312 が自身の recall
確認とともに決める事項である。OR ゲートは #146 の事情で存在している
ためである。

### 一つの病的な候補が約2秒かかり、cap = 4 でも生き残る

残しておく価値のある異常: N5TM の ±100 Hz と ±50 Hz の行は、cap 4
を含む*すべての* cap で ~2 100 ms にあるのに対し、同じターゲットの
±250 Hz と ±25 Hz の cap 4 の行は 40–90 ms である。K9KFR にはこの
ようなプラトーはない。

読みとしては、±100/±50 Hz の窓にある一つの候補がそれだけで ~2 秒
かかり、そこでは上位4に入り、±250 Hz ではより強い候補に上位4から
押し出され、±25 Hz では窓の完全に外側になる、というものである。
これは、#310 が抑えるために存在する失敗モードの具体例である:
**一つの病的な false survivor が、本物の候補が最も安い試行をする
機会を得る前に、高価な depth 予算を消費してしまう。** 候補数を減らす
だけでは直らない — コストは母集団あたりではなく、候補あたりである。

これは同じ呼び出しの中での比較 (25×) なので、ここで絶対的なホスト
wall-clock を信頼できなくしているホストの電源状態による交絡ではない。
ただし、絶対的なミリ秒は、誰かがそれをもとに推論する表に載せる前に、
Ryzen 9 機で測るべきである。
## 11. Ryzen 9 ランブック — 大型マシンが必要なものとその理由

ラップトップでは完了できない作業が3つある。2つは実時間（wall-clock）
がボトルネックで、1つは絶対タイミングの信頼性がボトルネックである
（Apple 製ラップトップは AC/バッテリ状態によってホストの実時間が約3倍
変動するため、本ドキュメント中で重要な絶対ホスト値はすべて Ryzen 9
機から取ることになっている — `BENCHMARKS.md` が測定マシンを記録して
いるのも同じ理由による）。

いずれも `embedded-poc/assets/*_sweep/` 配下にコーパスがある状態で実行する。

### 11.1 Tier-C 感度スイープ — `v0.10.0` のリリースゲート

**タグ付けの前に必須**（`CLAUDE.md`「Releases」）。2026-08-19/20 に、
Ryzen 9 9900X（24 スレッド）で全7プロトコルについて完了した —
`scripts/run-sensitivity-sweeps.sh` を、人間が毎回目視で読み直す表
ではなく自己 diff 式のリグレッションチェック
（`scripts/sweep-regression-check.py` +
`docs/notes/sweep-baseline.json`、設計はそのスクリプト自身の doc
コメントを参照）へ作り替えた、より大きなセッションの一部として実施した。

```sh
scripts/run-sensitivity-sweeps.sh
```

WSPR/FT8/JT65/JT9/Q65/MSK144 は再測定不要だった — それらの数値を最初に
取ったコミットとのソース diff により、以降どのデコード経路にも機能的
変更がないことを確認した（`wspr::ddc` と
`engine::dsp::{analytic,msk}` は `SAMPLE_RATE_HZ` のリネーム、#321
のみ — 値は同一）。FST4 だけは、`fst4::rung_major`、`engine::sync`、
`engine::llr` がこのサイクルで実際に変わったため（`Schedule::PhaseSplit`
#317、coarse_sync の dedup 修正 #316、npre1/npre2 OSD の移植）フルで
再実行した。結果：**FST4 の20個（モード × チャネル）の 50% crossing
はすべて、変更前の測定とバイト単位で一致した** — #317 と #316 がいずれ
も recall 中立になるよう特に作られ検証されていた（それぞれの ROADMAP.md
エントリを参照）ことと整合しており、今回は両者自身の的を絞った等価性
テストだけでなく、実際のスイープを通じてエンドツーエンドで確認された。
FST4-15 の AWGN crossing（−20.70 dB）と残り4つのサブモードは、いずれ
も WSJT-X の公表値との間に従来からある 0.1〜0.6 dB のギャップ帯に収ま
っている（上記セクション5の表と照合済み）。`BENCHMARKS.md` の更新は
不要 — 何も動いていない。

FST4 グループ全体（全5サブモード × 4チャネル、6500 WAV）は、コード変更の
前後どちらでもこのマシンで端から端まで **1852〜1922 秒（約31分）** かか

いう概算とはまるで違う。その見積もりは測定ではなく、2回実行した実測値は
互いに整合している。

今後は、`run-sensitivity-sweeps.sh` が各グループの

baseline エントリがまだないグループ（新サブモード、初回実行）は、今回
と同様に必ずフルグリッドへフォールバックするので、crossing 自体が動か
ない限り、今後の FST4 スイープはここで測定した約31分よりかなり速くなる
はずである。

### 11.2 Near-threshold の sniper cap スイープ — #312 の未決の半分

セクション10は、強い信号での比較可能性の問いには答えたが、そこでは
recall の崖を見つけられなかった。こちらがそれを見つける：

```sh
cargo test -p mfsk-core --features full,internal-testing --release \
    --test fst4_sweep fst4_60_diag_sniper_cap_near_threshold \
    -- --ignored --nocapture
```

デフォルトのグリッドは 4セル × 4幅 × 6 cap。20トライアルのコーパスで
は 1 920 回の候補ループになり、実測で **M5 ラップトップ上で約2時間**。
テストを編集せず、`MFSK_CAP_SWEEP_CELLS`（`channel:snr`、カンマ区切り）、
`MFSK_CAP_SWEEP_WIDTHS`、`MFSK_CAP_SWEEP_CAPS` で絞り込むこと。

**暫定、96構成のうち4つ**（スモークテスト、ccir_moderate m25、20
トライアル — スイープが動くことの証明には十分だが、結論には足りない）：

| width | cap | raw | frac | recall |
|---|---:|---:|---:|---:|
| ±250 Hz | 4 | 17 049 | 0 % | **6/20** |
| ±250 Hz | 50 | 17 049 | 6 % | **9/20** |
| ±25 Hz | 4 | 1 755 | 5 % | **6/20** |
| ±25 Hz | 50 | 1 755 | 57 % | **9/20** |

**崖は存在する** — 4 に切り詰めると 9 件のデコードのうち 3 件を失う。
そして、これが何を追跡*していない*かに注目してほしい：recall は
**どちらの**幅でも cap 4 で 6/20、cap 50 で 9/20 であるのに対し、それ
らの点での保持率は一桁違う（0 % 対 5 %、6 % 対 57 %）。

これが全グリッドでも維持されるなら、セクション10の結論とは直接的な
緊張関係になる。セクション10は、偽生存者の*コスト*は保持率に追従する
と言っており、これは cap を幅から導出する方向を支持する。こちらは、
弱信号の*recall* は絶対数に追従すると言っており、これは幅に関係なく
ランク付き候補を最低何個は保持するかという下限を設ける方向を支持する。
両者は別の列であり、同時に成り立ちうる — そうであれば方針は
「recall には絶対下限、コストには割合」であって、どちらか一方だけでは
ない。これこそ大型マシンで決着をつけるべき点であり、VK3NV が実際に
尋ねた問いでもある（#312：*崖は幅を跨いで同程度の割合のところに位置
するか？* — 暫定的な答え：いいえ）。

### 11.3 #308 のタイミング効果をめぐる緊張の解消 — `fst4sim` が必要

セクション9の未解決の留保：このセルのどれも、#308 の 2/5 のタイミング
回復を再現しない。#308 は、トライアル 33/45/67 を名指しする
**セルあたり100トライアル**の生成で測定したのに対し、この環境のコーパス
はセルあたり20だからである。ラップトップでは検証できない — そこには
`fst4sim` がインストールされていない。

WSJT-X をビルドしたマシンでは：

**`TRIALS` は 2026-08-27 まで黙って無視されていた。** ジェネレータは
`TRIALS=20` を無条件に代入していたため、下のコマンドは20トライアルの
コーパスを生成し、そのことをどこにも表示しなかった。現在は
`${TRIALS:-20}` になっている（7つすべての `gen_*_sweep_wavs.sh` で）。
この日付より前に実行した人は、何を渡していても20トライアルを測定した
ことになる。

**別の out-dir**（2番目の位置引数）へ生成すること。セルは全トライアルが
既に揃っている場合にのみスキップされるので、既存の20トライアルのセル
は新しい数でセルごと再生成され、そこにあったファイルは新しい実現値で
上書きされる：その場で行うと、fst4 の tier-C コーパスを乱すことにも、
トライアルのインデックスをシャッフルし直すことにもなる（上記の罠1）。

```sh
# 100 trials per cell, at least the crossing band
TRIALS=100 scripts/gen_fst4_sweep_wavs.sh \
    "$HOME/src/WSJT-X/build_jt9/fst4sim" \
    embedded-poc/assets/fst4_sweep_n100

cargo test -p mfsk-core --features full,internal-testing --release \
    --test fst4_sweep fst4_60_diag_npre_baseline_scan \
    -- --ignored --nocapture          # re-locate the band: it moves with n

cargo test -p mfsk-core --features full,internal-testing --release \
    --test fst4_sweep fst4_60_diag_npre_timing_substitutability_ablation \
    -- --ignored --nocapture --test-threads=1
```

baseline スキャンを**先に**再実行すること：部分 recall の帯域はコーパス
生成の性質であり、別の生成のセルにアブレーションを向けるのは、再び罠3
になる。アブレーションのドライバ内のセル一覧は、スキャンが報告した
ものに更新すること。

これで決着がつくこと：シナジーの結果（4セル中2セル）が n=100 でも成り
立つかどうか、そして #308 自身の 2/5 が、名指しされたトライアルが実際に
存在する状態で再現するかどうか。

## 12. 安価な `i0` ランキング対網羅的リトライ — そして退化した指標 (2026-08-18)

VK3NV の #308 提案を測定した：#308 は WSJT-X の制御フローをそのまま
移植した（`i0`、`i0+1`、`i0-1` をフル深度で試し、成功したら短絡する）。
これは組込みの候補ループの 3.02× / 2.51× であり、`decode_rung_major`
が `offsets = &[0]` をデフォルトとする理由である。提案は、高価な処理の
前に安価な sync 情報が既に存在するのだから、オフセットを**ランク付け**
して最良のものだけをデコードできるのではないか、というものだった：

> `i0`、`i0+1`、`i0-1` を安価にスコア付けし、最良のタイミングを
> 選択/ランク付けして、高価なデコーダを最初は一度だけ走らせることは
> できないか？

```sh
cargo test -p mfsk-core --features full,internal-testing --release \
    --test fst4_sweep fst4_60_diag_i0_cheap_rank_vs_exhaustive \
    -- --ignored --nocapture --test-threads=1
```

### コストは計時ではなく計数である

指標は実時間ではなく**フル decode 単位**（1つの候補/オフセットの組に
対する `compute_llr` + BP/OSD ラダー）である。そのためこれらの数値は
マシンに依存せず、そのまま引用できる — 本ドキュメントの他のすべての
`loop_ms` 列がラップトップでは相対的な形状のみであるのとは違う。

### 確認すべき交絡 — そしてその確認方法についての訂正

`i0` はランク付けされずに届くわけではない。`i0` は
`fst4_sync_search` から来ており、その仕事は (Δf, Δt) グリッド上で
**コヒーレントな Costas 振幅を最大化する**ことである。`sync_quality`
は関連する情報を測っているので、これも `i0` でピークになると考えられ
る — そうなると `argmax nsync` はオフセット 0 に退化し、`cheap-rank ≈
base` は提案についての証拠ではなくほぼ同語反復になる。

これは現実的な危険であり、テストは現在 `argmax nsync == 0` を明示的に
**計数**し、95 % 以上で判定を `DEGENERATE RANKING` に短絡させる。

**訂正 (2026-08-18)。** このセクションの以前の改訂は、退化がすでに
実証されていると主張し、`units` 列から推論していた：あるセルで `base`
51 対 `cheap-rank` 52、別のセルで 38 対 38。**その推論は無効である。**
どちらの構成も候補ごとにちょうど1回の `decode_at` を行う — `base` は
オフセット 0 で、`cheap-rank` は argmax で — ので、ランキングがどの
オフセットを選ぼうと、両者の unit 数は*構造上*等しくなる。カウントが
乖離するのは、2つのオフセットが `nsync` ゲートの反対側に落ちる場合だけ
である。unit が等しいことは、ランキングが異なる選択をしたかどうかに
ついて何も語らない。

証拠は実際には逆を指している：`nsync picked the winning offset first`
の行は AWGN m28 で 2/3 と 2/2 に達しており、ランキングが常にオフセット
0 を返すならこれはあり得ない。**したがって、退化はおそらく起きておらず、
明示的なカウンタを実行するまでは問いは未決である。**

そのカウンタを読む人のための、指標についての第2の注意：一致は**候補
ごと**に、recall は**トライアルごと**に数える。ランキングが勝ちオフセッ
トを選んだ候補も、同じトライアルの別の候補がすでにオフセット 0 で
デコードしていれば、decode を1つも追加しない。2つの列は直接比較でき
ず、高い一致率と `cheap-rank == base` の recall が同時に出ても矛盾では
ない。

### ランキングが退化していてもいなくても成り立つこと

ランキングが退化しているかどうかにかかわらず、`i0` の出どころから1つ
のことが導かれる：**「どのタイミングがデコードできるか」の安価な代理
指標が、別の sync 強度指標である可能性は低い**。refine 段がすでにそれ
を最大化しているからである。代理指標が機能するとすれば、有望な方向は
sync と直交するもの — Costas 相関ではなく、LLR の信頼度統計や、切り
詰めた BP のシンドローム重みである。

### 結果、20トライアルのコーパス、全8ラン

recall / decode unit。`argmax` カウンタが存在する前に測定したので、
一致列がこの表で利用できる唯一の代理指標品質のシグナルである：

| cell / OSD | base | exhaustive | cheap-rank | progressive | nsync picked winner |
|---|---|---|---|---|---|
| ccir-mod m24 / npre | 17, 51u | **18**, 83u | 17, 52u | 18, 86u | 0/6 |
| ccir-mod m24 / unpruned | 19, 51u | 19, 75u | 19, 52u | 19, 77u | 0/5 |
| ccir-mod m25 / npre | 7, 38u | **8**, 96u | 7, 38u | 8, 96u | 0/1 |
| ccir-mod m25 / unpruned | — | — | 8, 38u | **10**, 89u | 1/5 |
| AWGN m27 / npre | 12, 26u | **13**, 46u | **13, 26u** | 13, 44u | 1/1 |
| AWGN m27 / unpruned | 13, 26u | **15**, 42u | 13, 26u | 15, 39u | 1/3 |
| AWGN m28 / npre | 3, 23u | **6**, 61u | 3, 23u | 6, 60u | 2/3 |
| AWGN m28 / unpruned | 4, 23u | **6**, 60u | 4, 23u | 6, 59u | 2/2 |

**`cheap-rank` は8ランのうち1ランで `exhaustive` に一致した**（AWGN
m27 / npre：base のコストで exhaustive の recall、つまり 26 unit で
13/20）。残り7ランでは `base` に一致した。8回中1回の命中は機能する
代理指標とは言えないが、最初の3ランが示唆した完全な null でもない。

上記の未決の問いとは独立に成り立つ結果が2つある：

- **網羅的リトライは decode unit で base の 1.6〜2.7 倍のコスト**で、
  +1〜+3 件のデコードを得る。アルゴリズム呼び出し回数で測っているので
  マシン間で通用し、CoreS3 で測った 2.5〜3 倍の実時間と同じオーダーで
  ある。
- **`progressive` はコストで `exhaustive` に勝つことがない**（86 対 83、
  96 対 96、44 対 46、39 対 42、60 対 61、59 対 60）— どちらの向きにも
  せいぜい数パーセントで、集合を変えられない並べ替えとしてはノイズの
  範囲内である。ハーネスの確認にはなっている：recall は、そうなるべき
  とおり、全ランで `exhaustive` と一致する。

AWGN のセルは CCIR-moderate のもの（+1）より多く救う（m28 で +3）。これ
は #308 の出発点となったフェージング動機の枠組みとは逆であり、n=100 で
再確認する価値がある。

## 13. スケジューリングの決定 — `offsets` がオフセットメジャーのままである理由 (2026-08-18)

Issue #310 は、`decode_rung_major_timed` の `offsets` パラメータを
コスト順の優先度キューに畳み込むことを提案した。5段のラダー全体を
`offset = 0` で走らせてから `offset = -1` の最も安い段に触れる、という
やり方ではなく、「全候補にわたる安価な試行を先に → タイミングの代替 →
より深い相関 → 予算が許す限り OSD/フォールバック」とするためである。

**現在の立場：畳み込まない。オフセットメジャーの構造を保ち、代わりに
オフセット間に予算ゲートを追加する。** Issue の元の枠組みに反する
ので、根拠とともにここに記録する。上の測定セクションから再導出しなく
て済むようにするためである。

### これが依拠する3つの測定

1. **タイミングの多様性は高価で薄い**（§12）。網羅的な `{0,+1,-1}`
   リトライは、`{0}` の **1.6〜2.7 倍の decode unit** を要し、得られる
   のは **20トライアルあたり +1〜+3 件のデコード** — CoreS3 で測った
   2.5〜3 倍の実時間と同じオーダーで、呼び出し回数で測っているので
   マシン間で通用する。

2. **安価に狙い撃ちすることはできない**（§12）。オフセットを
   `sync_quality` でランク付けして最良のものだけをデコードしても、
   **8ランのうち1ラン**で exhaustive に一致し、残り7ランでは単一
   オフセットのベースラインに一致した。sync 由来のランキングが苦戦する
   と予想される構造的な理由がある — `i0` はすでにコヒーレントな sync
   スコアを最大化する `fst4_sync_search` から来ているので、機能する代理
   指標は sync と直交していなければならない。

3. **機構は相互作用する**（§9）。4セル中2セルで、タイミングの代替と
   unpruned-OSD フォールバックが一緒になって、どちらか単独では救えない
   トライアルを救う。

### 畳み込まない理由、重みの順

1. **最初の段のスイープが3倍になる。** rung-major の実際の貢献は、
   最初のデコードまでの時間に対する、順序に依存しない上界（41候補に
   わたる最初の段で予測約 7.4 秒）である。最も安い段にオフセットを混ぜ
   ると、この設計が提供するために存在する性質を手放すことになる。

2. **オフセットのセットアップは無料ではない。** 新しいオフセットは
   `symbol_spectra` とビットメトリクスを作り直す。オフセットをまたいで
   個々の段をインターリーブすると、20トライアル中 1〜3 件でしか報われな
   い機構のために、そのセットアップをすべての候補について、しかも早い
   時期に払うことになる。自然なスケジューリング単位は、自由なインター
   リーブではなく*オフセットのセットアップ + そのオフセットでの段の
   束*であり、これはまさにオフセットメジャーがすでにやっていることで
   ある。

3. **見返りを狙い撃ちできない。** 安価なランキングが機能するなら、慎重
   に選んだ1つの代替オフセットを前倒しするのは魅力的だろう。測定2は
   そうならないと言っており、したがって早期のオフセット作業は、実を
   結ぶところではなく広く費やされることになる。

### 代わりに作るもの

オフセットメジャーを保ち、**オフセット間にデッドラインチェック**を
追加する。`offset = 0` の全ラダーを完了まで走らせ、その後スロットの
残り時間を追加のオフセットに使う。これにより最初の段の上界が維持され、
高価な機構がクリティカルパスから外れ、スロットが逼迫しているときは
現行の `&[0]` の挙動へ縮退する。

**第2パスを追加するなら、タイミングと unpruned フォールバックを1つの
エスカレーション段階として一緒に追加すること** — 測定3は、2つのうち
安い方だけを足すと、本物のコストを払いながら利得の一部しか得られない
と言っている。測定が設計を確認するだけでなく変えたのは、ここだけで
ある。

関連：`npre` は、テストしたどのセルでも、unpruned 探索が取りこぼす
トライアルをデコードしたことがない（§9）ので、速度を買うのであって
recall は決して買わない。npre の*深さ*をタイミングとインターリーブする
理由はなく、安いから npre を先に走らせる、というだけである。

### 何がこれを覆すか

- 勝ちオフセットを実際に予測する **sync と直交する安価な代理指標**
  （LLR の信頼度統計、切り詰めた BP のシンドローム重み）。それにより
  狙いを定めた代替オフセット1つの前倒しが安くなり、コスト順の畳み込み
  が魅力的になる。
- シナジーのトライアルが 20 あたり 2〜3 件より実質的に大きな割合で
  あることを示す n=100 の実行（§11.3）。これは第2パスの価値を、より
  早く払うことを正当化できるほど引き上げる。
- オフセットごとのセットアップコストの直接測定 — 計装は
  `decode_rung_major_timed` の `clock` フックにすでに存在する — で、
  セットアップが1つの段に比べて小さいと示されれば、理由2を弱める。

3つとも未決である。この決定はそれらに対して暫定的である。

## 14. ソフトな Costas マージン vs 生の `nsync` (2026-08-18)

VK3NV の #310 の提案を実装し、測定した。
`engine::llr::sync_quality_generic` は既知の sync シンボルごとに 4 つの
トーンエネルギーをすべて調べるが、その後 `best == expected` 以外の
すべてを捨てる — そのため `E_exp = 9.8, E_wrong = 9.5` と
`E_exp = 9.8, E_wrong = 1.2` は同じ `+1` を寄与する。

`sync_quality_soft_generic`（新規、診断専用、decode パスからは何も
呼ばない）は同じ `nsync` を返し、**かつ**呼び出し側が与える
`[(E_expected, E_best_wrong); n_sync]` を埋める。スペクトルの追加計算は
ない — `symbol_spectra` がすでにこれらの値を生成している — し、ハード版
に対する追加コストはトーンごとに 1 回の比較だけである。ループが全トーン
に対する最大値と、期待トーン*以外*のトーンに対する最大値を同じ
パスで追跡するためである。バッファは確保せず呼び出し側が与える形に
しているのは、候補ループの中で候補ごとに `Vec` を持つ形が過去に問題を
起こしてきた組込みでも使えるようにするためである。

```sh
cargo test -p mfsk-core --features full,internal-testing --release \
    --test fst4_sweep fst4_60_diag_soft_costas_margin_separation \
    -- --ignored --nocapture
```

### 指標

**AUC** — （decode する候補, decode しない候補）のペアのうち、スコアが
正しく順序づけるものの割合。同点は半分と数える。0.5 が偶然水準である。
ここで適切な形なのは、#310 の想定する用途が候補をしきい値で切ることではなく、
エスカレーション予算のために候補を*ランキング*することだからであり、また
これらのセルが持つ強いクラス不均衡（decoder 約 15〜46 に対し non-decoder
約 700）の影響を受けないからである。

母集団: `nsync` ゲートを通過したすべての候補。partial-recall 帯、
`max_cand = 50`、sniper 形状で測る。「Decodes」は golden メッセージ
そのものを指す。

### 結果 — 提案は自身の kill 条件を通過する

| cell | candidates (dec / not) | `nsync` | mean margin | min margin | **mean logratio** |
|---|---|---:|---:|---:|---:|
| CCIR-mod m24 | 724 (46 / 678) | 0.767 | 0.784 | 0.697 | **0.786** |
| CCIR-mod m25 | 736 (18 / 718) | 0.701 | 0.779 | 0.718 | **0.800** |
| AWGN m27 | 742 (35 / 707) | 0.722 | 0.785 | 0.685 | **0.783** |
| AWGN m28 | 754 (15 / 739) | 0.701 | 0.706 | 0.593 | **0.727** |

- `mean logratio`（`ln(E_exp / E_wrong)` の平均、クランプあり）は生の
  `nsync` を**4 セルすべて**で上回る: +0.019、+0.099、+0.061、+0.026。
- `mean margin`（`(E_exp − E_wrong) / (E_exp + E_wrong)`）は 3 セルで
  明確に上回り、残る 1 セルでは並ぶ。
- `min margin` は**どこでも `nsync` より悪い** — 1 シンボルの悪さは、
  decode 可能な候補を見分ける要因ではない。

利得が最大になるのは recall が最も低いところ（m25: 0.701 → 0.800）で、
そこがまさにエスカレーション予算の対象となる領域である。したがって、
4 トーンの観測を 40 個のハードビットに畳み込むことは、使える情報を
*実際に*捨てており、上限のない対数比の形は有界な形よりもそれをうまく
使える。

これは変革ではなく改善である: AUC 0.78〜0.80 では、なお 5 分の 1 の
ペアを誤って順序づける。

### 両グループとも負のマージンを持つ

`mean(dec)` は −0.067 から −0.153、`mean(no)` は −0.260 から −0.267 の
範囲で、後に decode する候補でさえ、期待トーンは平均すると最強の
トーン*ではない*。これらの SNR では意外ではなく、分離は符号のテスト
ではなくマージンがどれだけ負かに宿る、ということである — しきい値に
手を伸ばす前に知っておく価値がある。

### #310 にとって重要なスコープの限界

この母集団は**ゲートを通過したすべての候補**であり、最初の rung で
安価に decode するものも含む。#310 の実際の問いはより狭い: *すでに*
安価な rung に失敗した候補のうち、高価な BP/OSD/タイミング予算に
値するのはどれか？ それはクラスバランスの異なる部分集合であり、
ランキングの振る舞いも異なるかもしれない。上の結果は、これを
エスカレーション優先度の信号として採用する上で必要条件ではあるが
十分条件ではない。

何にも配線されていない。`sync_quality` と `sync_quality_generic` は
手を付けておらずビット同一であり、ソフト版はテスト中のすべての候補で、
返す `nsync` がハード版のものと等しいことを assert する。

### #310 が実際にトリアージする母集団 — 結果は逆転する

§14 の母集団はゲートを通過したすべての候補で、`llra` で即座に decode
するものを含んでいた。それらはエスカレーション予算に到達しないため
スケジューリングの判断には無関係であり — かつ、集合の中で最も
易しい候補であるため — あらゆるスコアの見かけの利点を膨らませる。

`fst4_60_diag_soft_margin_escalation_priority` は母集団を、#310 が
トリアージしなければならないものそのものに絞る:

- **母集団**: `nsync` ゲートを通過し、*かつ* `offset = 0` の `llra` で
  BP に失敗したもの — 最も安価な rung であり、`decode_rung_major` の
  レイテンシ不変条件がすべての候補に保証するものである。
- **正例**: 完全なエスカレーション予算（`llrb`/`llre`/`llrc`、ゲートが
  選ぶ深さの OSD、および `i0 ± 1`）で最終的に decode するもの。
- **負例**: 一度も decode しないもの — それに費やした単位はすべて
  無駄だった。

| cell | post-first-rung candidates (decode) | `nsync` | mean margin | mean logratio |
|---|---|---:|---:|---:|
| CCIR-mod m24 | 220 (86) | 0.911 | 0.914 | **0.917** |
| CCIR-mod m25 | 203 (28) | **0.726** | 0.709 | 0.700 |
| AWGN m27 | 212 (66) | 0.879 | **0.905** | 0.887 |
| AWGN m28 | 194 (19) | 0.848 | **0.854** | 0.812 |
| **pooled** | **829 (199)** | **0.868** | **0.881** | 0.871 |

**§14 から変わる点が 2 つある。**

**1. この母集団は、3 つのスコアのどれでも非常にトリアージしやすい。**
プールした AUC は 0.87〜0.88 で、偶然水準をはるかに上回る。どのスコアが
勝つかとは無関係に、これは #310 にとって良い知らせである: 最初の rung
の後でも、エスカレーションする価値のある候補は、決して decode しない
ものと*見分けがつく*。

**2. ソフトマージンの利点は大部分が消える。** プールすると、`mean
margin` は生の `nsync` を **+0.013** 上回り、`mean logratio` は
**+0.003** 上回る — §14 の +0.019 から +0.099 に対して。しかも一貫性も
なくなる: `mean margin` は CCIR-moderate m25 で `nsync` に負け
（0.709 対 0.726）、`mean logratio` は 4 セル中 2 セルで負ける。最も
成績の良い定式化も入れ替わる — §14 では `mean logratio` がどこでも
勝ったが、ここではプールで `mean margin` が勝つ。

**VK3NV 自身の kill 条件では、これは不合格である。** 条件は次のとおり
だった: *生の `nsync` がすでに高価な偽の生き残りを分離できているなら、
ほかに何かを足す理由はない。* 重要な母集団ではそれができている —
プールで 0.868 — し、ソフトな特徴量が加える AUC は約 1 ポイントで
一貫せず、しかも候補ごとに 40 個の値の状態を余分に要する。

### 方法論上の要点、こちらのほうが持続する成果である

§14 の見かけの利得は、かなりの部分が誤った母集団で測ったことによる
アーティファクトだった。最初の rung で decode する候補 — どの
エスカレーション方針も目にしないもの — を含めたことで、マージンの
利点は約 5 倍に膨らんでいた。

VK3NV が提案の一部として `nsync` のみのベースラインを規定したのは
そのためである。それがなければ、`mean margin` のプール値 0.881 は
「ソフト特徴量はよく分離する」と読め、配線を正当化してしまう。
ベースライン 0.868 と並べれば「生の `nsync` がすでにこれをやっていた」と
読める。同じ数字で、判断は逆になる。

実装はツリーに残す（`sync_quality_soft_generic`、診断専用、何も呼ばない）。
否定的な結果を再導出できることに価値があり、また候補ごとのシンボル
ペアは、将来の代理指標の試みが欲しがる計装だからである。だがこの証拠
からは、#310 のエスカレーション順序は、すでに持っている `nsync` を使い、
より良い信号は別に探すべきである。

**未検証**: ペアの*学習された*組み合わせが `nsync` に勝つかどうか —
提案が当初掲げていたニューラルネットの枠組みである。手で選んだ 3 つの
定式化が失敗したことは、それに対する弱い証拠であり、強い証拠ではない。

### 訂正: ソフトマージンは `nsync` を超える情報を*持っている*

前節はソフトな特徴量は何も加えないと結論した。**それは誤りだった**。
そしてその誤り方には示唆がある: 無条件の AUC 比較では、「情報がない」と
「ベースラインとの相関で情報が隠されている」を区別できない。

`fst4_60_diag_soft_margin_conditional_value` は、より大きな母集団 — 6
セル、最初の rung 後の候補 1 263（386 が decode、877 が decode せず）、
3 つではなく 9 つの特徴量定式化 — で、これを 3 通りに検証する。

**1. 層別 AUC — `nsync` の値を固定した内側で。** ある特徴量が `nsync`
の代理にすぎないなら、`nsync` を一定に保てば言うことは何も残らず、
AUC は 0.5 に張り付くはずである。そうはならない:

| feature | unconditional AUC | **stratified AUC** |
|---|---:|---:|
| `nsync` (baseline) | 0.920 | — |
| mean margin | 0.932 | **0.717** |
| mean logratio | 0.926 | **0.704** |
| sum logratio | 0.926 | 0.704 |
| mean worst-10 | 0.913 | 0.689 |
| p25 margin | 0.916 | 0.638 |
| median margin | 0.917 | 0.579 |
| min margin | 0.724 | 0.542 |
| count margin>0 | 0.921 | 0.530 |
| margin variance | 0.345 | 0.412 |

`nsync` を固定した内側でも、正規化マージンの平均は、decode するものと
決して decode しないものを 0.717 で順序づける。**4 トーンの観測を
40 個のハードビットに畳み込むと使える情報を捨てることになる、という
VK3NV の指摘は正しかった。**

（`margin variance` は反転する — どちらの向きでも 0.5 を下回る — つまり
分散が*小さい*ことが decode と関連する。実在するが、ここでは
活用できない。）

**2. 当てはめた線形ルールと、それが実際に何をもたらすか。** `nsync` と
9 つの特徴量すべてに対するロジスティック回帰:

| | AUC |
|---|---:|
| `nsync` alone | 0.920 |
| in-sample fit (optimistic upper bound) | 0.935 |
| **2-fold cross-validated (honest)** | **0.934** |

したがって特徴量の全体を最適に組み合わせても、この crate がすでに
計算している `nsync` に対し **+0.014 AUC** の価値しかない。

### 決定は変わらない — ただし理由は「不在」ではなくコストになった

この実験の取りうる 2 つの結果は、どちらも同じ行動に至った。これは
手の込んだ版を走らせる価値があった理由でもあるので、明記しておく:

- 層別 AUC が約 0.5 だったなら、信号はない → `nsync` を使う;
- 実際は約 0.7 で、信号はある → **それでもコストの基準を満たさない** →
  `nsync` を使う。

`nsync` は経路上ですでに計算されている `u32` である。ソフト版の
代替は、候補ごとに 40 × 2 f32 = 320 B の状態を要し、しかもそれは
候補ループ内での候補ごとの確保が実害を起こしてきたターゲットでの話で、
さらに当てはめた重みと標準化定数は、サブモード、チャネル条件、
コーパスの世代をまたいで再検証し続けなければならない — 腐っていく
調整済み定数である。**+0.014 AUC はそれに見合わない。**

意図的にこう記録している: 「測定した。利得が 1.4 ポイントで、保守すべき
モデルに見合わないので採用しなかった」は、「3 つの式を試して負けた」
よりはるかに持続する答えであり、同じ提案が戻ってきたときにも答えに
なる。

**何が結論を変えるか**: ランキングの質が、小さな順序の改善ではなく
大きな実時間の節約に変わる用途 — たとえば、ランキングの上位 1 割
だけが実際に処理されるほどエスカレーション予算が厳しい場合。それは
`decode_rung_major_timed` の既存の `clock` フックから測定できるが、
まだ行っていない。

提案が当初掲げた非線形/学習版はこれで排除されるわけ**ではない**が、
コストの議論はそちらにこそより強く当てはまる。

### 予算曲線 — 順序づけが実際にどれだけの価値を持つか

AUC は順序づけの指標だが、#310 の通貨は**スロット締切までの decode 数**
である。両者をつなぐのは予算だけである: 予算がすべての候補をカバー
するなら、順序づけは何も変えない。ランキングの先頭しかカバーしない
なら、小さな順序の改善が大きく効きうる。だから上の AUC の結果だけでは
この問いに決着をつけられなかった。

`fst4_60_diag_escalation_budget_curve` は欠けていた量 — **候補ごとの
エスカレーションコスト** — を測定し、締切をシミュレートする。母集団は
最初の rung 後の集合である（`offset = 0` の `llra` rung は沈没コスト
である: レイテンシ不変条件がそれを全員に費やすので、予算の外にある）。
コストは、`llrb`/`llre`/`llrc` ＋ `i0`、`i0+1`、`i0-1` での OSD にわたる
（offset, stage）評価 1 回を 1 単位として数え、成功で止まる。
6 セル、候補 1 263、うち 386 が decode、合計 12 330 単位（候補あたり
平均 9.8）。

| budget | arrival order | `nsync` | mean margin | **oracle** |
|---:|---:|---:|---:|---:|
| 10 % | 49 | 166 | 172 | **358** |
| 20 % | 111 | 288 | 306 | 386 |
| 30 % | 165 | 361 | 365 | 386 |
| 40 % | 187 | 377 | 382 | 386 |
| 50 % | 198 | 380 | **386** | 386 |
| 70 % | 316 | 384 | 386 | 386 |
| 100 % | 386 | 386 | 386 | 386 |

`oracle` = decoder を先に、最も安価な decoder を最初に。達成不能である
— 答えを知っている — が、*あらゆる*ランキングが得られるものの上限を
与える。

**3 つの点が浮かび上がる。**

**1. 優先度の信号があること自体が非常に価値が大きい。** 予算 10 % では、
`nsync` は 166 の decode を返し、到着順の 49 に対して 3.4 倍になる。
ほかに何が真であっても、#310 のエスカレーション順序づけのアイデアは
健全である。

**2. ソフトマージンの利点は小さいままだが、ゼロではない。** 10 % で
+6 decode、**20 % で +18**（306 対 288、相対 6.3 %）、30 % で +4、
そして 50 % では oracle の上限に達するが、`nsync` はまだ 6 足りない。
+0.014 AUC と整合しており、コストの判定は変わらない: 1 つの予算点での
386 中 18 decode は、候補ごとの 320 B と保守すべきモデルに見合わない。

**3. 興味深い数字は oracle との差であり、それは大きい。** 予算 10 % で
oracle は 386 中 358（93 %）を回収するのに対し、`nsync` は 166（43 %）
にとどまる。どちらのスコアも近くない。その余地が存在するのは、oracle
が decode 可能性だけでなくコストでも並べ替えるからである — **安価な
decoder は高価なものよりも単位あたりの価値がはるかに大きく、`nsync`
もマージンもコストについては何も知らない。**

したがって #310 にとって有用な方向転換は次のとおりである: **欠けている
信号は「これは decode するか」ではなく、「これは安価に decode するか」
である。** ここにある両スコアは前者を予測する。コストは部分的に構造的
であり、decode 可能性よりも予測が安くつくかもしれない — `nsync` は
すでに OSD が走るかどうか自体を決めており（`osd_attempt_min`）、高価な
段は OSD である。

### これを釣り合いの取れたものにとどめる但し書き

FST4-60 の実際の状況は、およそ 7 s の余裕に対し 13.6 s の `no8_osd`
候補ループ — 予算にして約 50 % といったところである。**50 % では、
`nsync` はすでに 386 中 380（98.4 %）を返す。** 劇的な順序づけの効果は
10〜20 % の予算に現れるもので、それはこのモードが実際に持つ締切より
数倍厳しい締切を意味する。

つまり: 順序づけは持つ価値がある（点 1）、実在する予算では `nsync` で
その分は足りている、そして oracle との差（点 3）を追う価値が出てくる
のは、予算がずっと厳しくなる場合のみである — より短いサブモード、
より遅いターゲット、またはここで使った sniper 形状の 50 よりはるかに
大きい wideband 候補リスト。

### 幅優先 vs 深さ優先 — 順序づけよりスケジュールのほうが重要

上の予算曲線は**深さ優先**のエスカレーション（各候補が、次が始まる前に
成功までラダーを実行する）を使った。`decode_rung_major` は**幅優先**
（1 つの rung をすべての候補にわたって走らせてから、どれかが下に降りる）
なので、それらの順序づけの結論を、確認せずに設計へ持ち込むことは
できなかった。`fst4_60_diag_budget_curve_breadth_vs_depth` は、同じ候補
と同じ段ごとの結果に対して両方のスケジュールを走らせる。

ラダーは §13 に従い offset-major である: `i0` での `llrb`/`llre`/`llrc`/OSD
（`llra` rung は沈没コスト）、次に `i0+1` での完全な 5 段、次に `i0-1`
でも。候補 1 263、386 が decode、12 330 単位、最長のラダーは 14
段。

| budget | depth: arrival | depth: `nsync` | depth: oracle | breadth: arrival | breadth: `nsync` | breadth: oracle |
|---:|---:|---:|---:|---:|---:|---:|
| 10 % | 49 | **166** | 358 | 35 | 35 | 35 |
| 20 % | 111 | **288** | 386 | 80 | 80 | 80 |
| 30 % | 165 | **361** | 386 | 137 | 150 | 152 |
| 40 % | 187 | 377 | 386 | 350 | 350 | 350 |
| 50 % | 198 | **380** | 386 | 350 | 350 | 350 |
| 70 % | 316 | 384 | 386 | 360 | 366 | 366 |
| 100 % | 386 | 386 | 386 | 386 | 386 | 386 |

**1. 幅優先では、順序づけは本質的に何もしない。** 3 つの順序づけは
10 % と 20 % で同一で、それ以外でもどこでも数 decode 以内に収まる。
理由は機械的である: 予算 10 % で 1 263 の stage-0 評価のうち約 1 233 を
賄えるので、候補を訪れる順序に関係なく、ほぼすべての候補が最初の
エスカレーション段を得る。**「生き残りを `nsync` で再ソートする」という
アイデアは rung-major では死んでいる** — 何も得られず、正当化しなければ
ならないことが 1 つ減る。

**2. 幅優先は厳しい予算の下で著しく悪い。** 10 % では、`nsync` 付きの
深さ優先が 166 decode を返すのに対し幅優先は 35、20 % では 288 対 80、
現実的な約 50 % では **380 対 350** である。

**3. 機構は OSD の段である。** 幅優先が予算 30 % と 40 % の点の間で
137 から 350 に跳ぶのは、段の境界である: stage 0〜3（OSD を含む
offset 0 のラダー）を 1 263 の候補にわたって走らせるのに最大でも
4 x 1 263 = 5 052 単位かかり（実際はそれより少ない: decode した候補はそこで
止まり、`osd_attempt_min` に満たない候補には OSD の段がない）、40 % が賄う
4 932 単位と同程度の大きさである。この走査にはそのくらいが必要であり、
30 % の点の 3 699 では届かない。それ以下では、幅優先は
予算の全部を安価な BP の段に使い果たしており、**誰に対しても OSD に
到達していない** — そして OSD こそ、これらの decode の大半が生まれる
場所である。最も収穫の多い段を、すべての候補があらゆる安価な段を経る
まで後回しにすることは、まさに幅優先の目的であり、締切の下では
まさに decode を犠牲にする。

### これが定量化するトレードオフと、そこから得られる設計

これは rung-major に反対する議論ではない。rung-major が存在するのは、
**time-to-first-decode の順序に依存しない上界**のためである — 深さ優先
にはそのような保証がなく、悪い候補順は最初の decode を際限なく遅らせる
（先に測定した最悪ケースでは、合計 30.15 s のうち約 30 s）。2 つの性質は
本当に緊張関係にあり、上の数字がその代償である:

| | time-to-first-decode | decodes at ~50 % budget |
|---|---|---|
| breadth-first (rung-major) | **bounded by one rung** | 350 / 386 |
| depth-first + `nsync` | unbounded (ordering-dependent) | **380 / 386** |

**両方を同時に得ることができ**、§13 にすでに記録されているフェーズ分割が
その場所である:

- **Phase A — 最初の rung、幅優先、無条件。** `offset 0` の `llra` を
  すべての候補にわたって。これが*まさに*レイテンシ不変条件である:
  順序づけによらず、すべての候補が有界の時間内に最も安価な試行を得る。
  そのまま維持する。
- **Phase B — エスカレーション、深さ優先、`nsync` で順序づけ、予算で
  ゲート。** 上界が守られた後は、幅優先にもう利点は残らず、現実的な
  予算では 30 decode を失う。ここでは `nsync` は無料である — Phase A が
  ゲートを走らせるためにすべての候補について計算済みだからである。
- **Phase C — 第 2 パス（代替タイミング*と*枝刈りなし OSD を一緒に、
  §9 に従う）、予算が残る場合のみ。**

したがって「エスカレーションのフェーズは `nsync` で再ソートすべきか」
への答えは、**yes、ただし Phase B が深さ優先であるべきだからに限る** —
幅優先の下ではソートは無価値である。2 つの決定は結合しており、どちらも
単独では正しくない。

未測定: これはエスカレーションを逐次の単位としてモデル化しており、
§13 の理由 2 が鍵とする offset ごとのセットアップコスト
（`symbol_spectra` ＋ bit-metrics の再構築）を無視している。したがって
Phase C のコストはここでは過小評価されている。

| coarse search | 192 ms | スロット終了後 (デュアルコア fill) |
| refine、全候補 | 552 ms | スロット終了後 (デュアルコア) |
| 生存候補の refine + デコード (2 デコード) | 130 ms | スロット終了後 |
| **スロット終了後の合計** | **874 ms** | |

そこに至った変更は3つで、いずれもアルゴリズムではない — 2つはデフォルトが
opt-in からオンに反転しただけ（`SlotCapture`、`coarse_search`、`refine_all` は
帯域に依存しないので、スイッチは既にこの経路に届いていて、単にオフに
なっていた）、もう1つは、捨てられていたバッファを捨てなくなったことである:

| | バッチ、シングルコア | ストリーミング | + デュアルコア | + 二重 refine の除去 | + SIMD sync 探索 |
|---|---:|---:|---:|---:|---:|
| DDC + スペクトログラム | 1314 (スロット終了後) | 1539 (キャプチャ中) | 1539 (キャプチャ中) | 1539 (キャプチャ中) | 1539 (キャプチャ中) |
| coarse search | 394 | 249 | **192** | 191 | 192 |
| refine、全候補 | 1357 | 1348 | **853** | 866 | **552** |
| 生存候補の refine + デコード | 300 | 289 | 289 | **130** | 130 |
| **スロット終了後の合計** | **3365** | **1886** | **1334** | **1187** | **874** |

どの列でも、同じ周波数の同じ 2 デコードが得られた。
`MFSK_FST4_DDC_BENCH_STREAM=0` / `_DUAL=0` で最初の2列に戻せる。

**二重 refine は、5 倍間違った数値によって正当化されていた。**
ステージ 2a はすべての候補を refine し、`(freq, i0, score)` を保持して、
それぞれの `cd0` を捨てていた。その理由は、保持すると「1つあたり ~266 KB」
かかるから、というものだった。ステージ 2c はその後、生存候補のものを
1つあたり 80 ms で作り直していた。実測すると、refine 済みベースバンドは
**52 KB** である — どの帯域も同じ `REFINE_DS_RATE_HZ` にデシメートされるので、
帯域によらず複素サンプル ~6 667 個になる。sniper の 2 候補なら、予算 1792 KB
に対して 104 KB であり、しかも `ddc_refine` は変化しない 3 つの入力に対する
純粋関数なので、作り直しはビット単位で同一のバッファを再計算していたに
すぎない。`refine_all` は今では空き PSRAM を測り、収まるならそれらを保持する。
これがステージ 2c を 289 から 130 ms にしている。

wideband 経路の 50 候補では、同じチェックが「収まらない」と判定する: 2.7 MB
に対して、PSRAM には既にスロットとそのスペクトログラムが載っている。予算は
定数ではなく最大の空きブロックの 3 分の1である。目的は推測ではなく
「余地があるか」に答えることだからだ。

キャプチャ側の合計がバッチの DDC 単独より大きい — 1539 対 1314 ms — のは、
かつて `coarse_sync` の内部で行われていたスペクトログラムの構築を今は
含んでいるからである。仕事は同じで、余地のある場所で支払っている。

2 候補の `refine_all` は 1/1 でコアに分かれるので、理想は ~674 ms のはずで、
実測の 853 ms にはディスパッチと、PSRAM 上で 2 つのコアが互いに与える
影響が含まれる。2x ではなく 1.58x である。wideband 経路の 50 候補では分割は
均等で、ディスパッチは合計の中に埋もれる。

**ドット積カーネル上の `fst4_sync_search`。** そのスコアラは、288 サンプルの
Costas ブロックに対する `Σ cd0[n]·conj(ref[n])` で、候補ごとに 2 235 回
実行される。書き下すと、その実部と虚部はそれぞれ、同じインターリーブ済み
メモリ上の*実*ドット積である — 虚部の方は、サンプルを `(re, im)` →
`(−im, re)` に書き換えた参照に対するもの — ので、スカラの複素ループ1つが
`dot_f32` の 2 回の呼び出しになり、flop 数は同一で、このチップでは
それが `dsps_dotprod_f32_aes3` になる。候補あたりの `fst4_sync_search` は
**711 → 419 ms** になった。wideband の候補ループ全体は 32.8 → 25.7 s、
最初のデコードは 2301 → 1966 ms である。

この計測に必要だったことが 2 つある:

- **参照は周波数オフセットごとではなく、一度だけ確保する。** 探索は
  候補ごとに 40 個のオフセットを掃引する。オフセットごとに新しい
  バッファ対を確保すると、~2.3 KB の確保が 400 回になる。
  `CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL = 4096` のもとでは、それらは内部 DRAM
  が残っている間は内部 DRAM に、なくなれば PSRAM に置かれるので、同一の
  コードが、DRAM に余裕のあるベンチでは候補あたり 780 ms、DRAM を WiFi と
  タスクスタックに使い果たしたアプリケーションでは 1131 ms と計測された。
- **ベンチとアプリケーションは今も食い違っていて、その理由は移った。**
  キャプチャタスクを止める (`MFSK_FST4_APP_CAPTURE_SLOTS=1`) と、アプリは
  ベンチと完全に一致する — ループ 25.8 s、候補あたり sync 探索 419 ms。
  キャプチャを動かすと、同じビルドが 1060 ms を計測する。この作業の
  初期には、同じ実験でキャプチャの並行動作は*まったくコストにならない*と
  出ていて、それは当時は正しかった: 内部 DRAM の枯渇が支配的で、それを
  覆い隠していたのである。それを直し、さらに内部ループを演算律速から
  帯域律速にしたことで、キャプチャ/デコードの PSRAM 競合が最上位の項目に
  繰り上がった。**反証された仮説も、ボトルネックが移れば正しいものに
  なりうる。**

### キャプチャ/デコードの PSRAM 競合 — 2度攻めた、そして計測上の問題

アプリケーションの候補ループは、同一の仕事でベンチの 25.7 s に対して
43-51 s であり、キャプチャタスクを止めるとその差は完全に埋まる
(`MFSK_FST4_APP_CAPTURE_SLOTS=1`: 25.8 s、候補あたり sync 探索 419 ms。
キャプチャ動作中は 1060-1352)。この効果は実在し、大きい — そのステージで
2.5-3.2x — うえに、スケジューリングではなく帯域の問題である: 先のコミットが、
無線を黙らせ、停止させ、無線なしで単なる内部 DRAM の確保だけで、遅延の
全体を再現することでそれを確立している。

2つの対策を、どちらも計測したが、どちらも採用しなかった:

1. **到達可能なスパンを1つの連続バッファに集める。** 探索は 53 KB の
   ベースバンド全体に点在する ~620 サンプルの窓 5 つに触れる — 生きた
   データは 25 KB — ので、候補ごとに1回まとめてコピーすればコストは
   ~25 µs である。計測は、それなしの版の 1060 に対して候補あたり
   1174 ms だった。**決着がつかず**（下記参照）、それ単独では何も得られない
   ので、リバートした。
2. **その集めたバッファを内部 DRAM に置く。** `.bss`、コアごとに1つ
   (合計 51 KB)。これは探索が候補ごとに 2 235 回読むバッファなので、
   競合するバスから外せばそれで全部解決するはずだった。結果は**悪化し、
   しかもメカニズムまで説明できる**: キャプチャ開始時の内部 DRAM は
   159 -> 107 KB に減り、*ポリフェーズ再センタリング* — まったく別の
   ステージ — が 419 -> 861 ms になった。これは本ファイルが既に文書化して
   いる内部 DRAM 枯渇の兆候である。リバートした。**律速している制約は
   内部 DRAM であり、このシステムはそれを既に最も効果の高い場所に
   使っている**。それ以上を注ぎ込んで速度を買っても、得るより失う方が大きい。

**そして、この精度では単発の A/B は成立しない。** *同一*のバイナリを
2回走らせて、ループは 43.8 s と 51.3 s、sync 探索は候補あたり 1060 と
1352 ms を計測した — 28% の幅で、上記の差より大きい。`recentre` は同じ
2回の間で安定していた (421 対 419 ms) ので、分散は帯域競合のあるステージに
固有で、おそらくデコードとキャプチャタスクのブロック境界との間の位相に
依存する。試行 1 の「劣化」はその幅の内側にあり、劣化として読んではならない。
試行 2 のものは違う。その根拠は、別のステージが倍になったことと、52 KB の
内部 DRAM が消えたことだからである。

これ以上ここで進めるには、変種ごとに1回の実行ではなく、複数スロットに
わたる中央値が要る。

**残っていること**を順に挙げる: キャプチャ/デコードの PSRAM 競合
（上記 — 最初のデコードはどちらでも ~2.0 s で影響を受けない。次のスロットの
キャプチャが本格化する前に着地するので、これが損なうのはレイテンシではなく
カバレッジの時間である）; 次に、競合なしで候補あたり 419 ms の
`fst4_sync_search` が、依然として候補あたり最大の項目; その次に、依然として
シングルコアのステージ 2c で、130 のうち ~60 ms 分の価値がある。

### ベンチではなく、受信機アプリケーションで

WiFi が接続され、LCD が描画され、*次の*スロットのキャプチャが並行して
動いている状態の `fst4-app` — つまり実際の運用条件:

| | |
|---|---:|
| 最初のデコード、スロット終了後 | **2392 ms** |
| 全 50 候補 | **37.6 s** |
| キャプチャのフロントエンド | 5.5–6.4 s (9–11% のデューティ) |

32.8 → 37.6 s の差は並行するキャプチャによるもので、ベンチが行わない
実際の仕事である。

### そこに至るまで

最初のデコードまでのスロット終了後の時間は、2026-08-21/22 の間に
**5207 → 2301 ms** になった。それぞれの価値の大きい順に:

| 変更 | 動いたもの | PR |
|---|---|---|
| キャプチャ時スペクトログラム | フロントエンド (4818 ms) がスロット終了後の予算から完全に外れる; 同じデフォルトが届いたとき sniper は スロット終了後で 3365 -> 1886 ms | #336, #348 |
| `coarse_sync` の dedup の脱二次化 | ランキング 2989 → 292 ms | #342 |
| デュアルコアの相関 fill | fill 1131 → 714 ms | #342 |
| ランク階層化されたデコード深度 | 最初のデコードは不変、閾値 recall 22 → 60 / 68 | #341 |
| 内部 DRAM の回収 | アプリのループ 53.6 → 37.6 s、`fst4_sync_search` 1929 → 778 ms/cand | #347 |

このうち2つは、ここで他の何かを最適化する前に読み直す価値がある。どちらも、
自明な説明が計測され、それが間違っていたからである:

- wideband の探索は相関律速では**なかった**。分割してみると、fill は
  1131 ms、*ランキング*は 2989 ms — ~15k 候補に対する O(n²) の dedup
  だった。これは、§earlier work がスペクトログラムのワーキングセットのせい
  だと暫定的に見ていた、sniper との bin あたり 3.2× の差も説明する:
  bin あたりの fill コストは両者で同一 (0.60 ms/bin) である。
- アプリケーションの遅延は無線のせいでは**なく**、自身のキャプチャタスクの
  せいでもなかった。内部 DRAM だった: `CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL=4096`
  のもとでは、すべての小さな確保は内部 DRAM を優先し、それが尽きると黙って
  PSRAM にフォールバックする。無線が存在しない状態で 132 KB の内部 DRAM を
  確保しておくと、33 → 54 s の遅延の全体が再現する。

## 16. blind CQ の AP パスはほぼ無料で、FST4 には要らない (2026-09-13)

FT4 と FST4 は同じ変更で常時オンの blind CQ a-priori パスを得た —
本家の `iaptype = 1`、局の知識をまったく使わずにメッセージ型と `CQ`
接頭辞だけを固定するパスで、mfsk-core は「呼び出し側が hint を渡した
ときだけ AP を走らせる」実装だったため一度も走らせていなかった。

FT4 ではこれが AWGN で 1.11 dB の価値があった (`FT4_BENCHMARK.md` §48)。
FST4 では測定可能な価値がゼロで、面白いのはその理由である。

**スイープ (全5サブモード、2026-09-13、baseline `c7acb4da`):**

| サブモード | AWGN | CCIR good | CCIR moderate | CCIR poor |
|---|---:|---:|---:|---:|
| FST4-15 | −0.03 | +0.00 | −0.10 | +0.00 |
| FST4-30 | +0.00 | +0.00 | −0.08 | −0.05 |
| FST4-60 | +0.00 | −0.05 | +0.00 | +0.00 |
| FST4-120 | +0.00 | +0.00 | +0.00 | +0.00 |
| FST4-300 | +0.00 | +0.00 | +0.00 | +0.00 |

20セル中、悪化ゼロ、12セルは完全一致、6セルが 0.03-0.10 dB 改善 —
セルあたり 180-900 試行では補間の粒度であって利得ではない。コーパスは
`CQ JL1NIE PM95`、FT4 の数字を大きくしたのと同じ CQ のみの最良条件
なので、「事前分布が当てはまらなかった」という話ではない。

**平坦な理由: FST4 のラダーが既にそのデコードを取っている。** FST4-60
AWGN コーパスで、各デコードをどの段が取ったかを数える (各点20ファイル):

| SNR | デコード数 | 勝った段 |
|---:|---:|---|
| −26 dB | 19/20 | 1×3, 2×3, 5×4, 6×9 |
| −27 dB | 17/20 | 2×3, 5×9, 6×4, **12×1** |
| −28 dB | 7/20 | 2×2, 4×1, 5×4 |
| −29 dB | 1/20 | 4×1 |

pass 12 が blind CQ 仮説。80ファイル中1回しか発火しない。段は配線されて
いて到達可能である — 死に枝ではなく、この確認自体に意味がある。**到達
していない段はスイープ上まったく同じに見える**からだ。単に、上にある
nsym=4 LLR ラダーと zsum-OSD (§8) が到達時点で既に収束しているので、
ほとんど勝てないだけである。FT4 のラダーにはそこに実際の穴があった。
FST4 には無い。

**しかもほぼ無料。** この段は `process_candidate_basic` の最後にあるので、
デコードできた候補は到達しない。上の全段で失敗した候補だけが払う。
したがって最悪ケースは「全候補が全段で失敗する閾値以下のスロット」。
FST4-60 AWGN の −29/−30 dB の40ファイル (合計1デコード) で、パスあり/
パスを取り除いた場合を計測:

| | 実時間 |
|---|---:|
| blind CQ あり | 30.67 s |
| ablate | 30.21 s |

1.5%、recall は同一。これが効くのは host ではなく組込み側である:
issue #306 で病的な false survivor が ~14 秒、実デコードが ~55 ms と
測っており、「survivor だけで走る段」は本来警戒すべき形をしている。
これはそれに当たらない。

**それでも残す。** 最悪 1.5%、感度は中立、そして本家が走らせている —
`fst4_decode.f90` は `ft4_decode.f90:328` と同様、毎デコードで AP パスを
走らせる。WSJT-X からの逸脱には理由が要るが、「CQ のみのコーパスで
利得が測れなかった」は理由にならない。混在トラフィックでは、このパスは
「本家の仮説集合を試す」か「何も試さない」かの差になる。
## 17. オンデバイスの bring-up ログ — EMBEDDED.md からここへ移動 (2026-09-16)

以下の18個の番号付き試行は、もともと `EMBEDDED.md` の
`## FST4 on embedded` セクションだった — 782 行、その文書の 39%。
試行は見出しではなく太字の段落として書かれていたため、どのアウトラインにも

役割にあたる。リファレンスマニュアルには結果としての状況とここへのポインタが残る。

原文のまま移動した。ある試行が「Seventeenth attempt が締めくくった数値と
同じ」と述べている場合、その Seventeenth attempt は他所ではなく、下にある。


3つ目の、これまでとは別個の組込みの物語 — issue #306 がそもそも実現可能かを

   自身のログ出力用には正しく自動検出しているにもかかわらず、アプリ
   イメージのヘッダに 4 MiB のフラッシュサイズを書き込む。**
   `fst4-bench` 以前にこの CoreS3 へ書き込まれたアプリはたまたますべて
   合計 4 MiB（factory + littlefs）に収まっていたため、これはずっと
   黙って誤っていたが問題にならなかった — このベンチが必要とした
   9 MiB の factory パーティションが、それを暴いた最初のものだった
   （`E (NN) boot: Failed to verify partition table` /
   `flash_parts: partition N invalid ... exceeds flash chip size
   0x400000`。不正なヘッダは再ビルドのたびに付いてくるため、
   `espflash erase-flash` を丸ごと実行しても持続した）。
   `embedded-poc/scripts/flash-monitor.sh` で修正した — 任意の6番目の
   引数 `FLASH_SIZE`（この基板では `16mb`）を取り、明示的な
   `--flash-size` フラグになる。診断はスクリプト自身のコメントを参照。
   これを渡さない従来の呼び出し側は、以前の（バグだがこれまでは
   無害だった）挙動のまま。
2. `m5stack-cores3-app/partitions.csv` の `factory` パーティションを、
   ベイクしたアセットが生む約 7.7 MiB のアプリイメージのために
   3 MiB から 9 MiB へ拡大した — そのクレート内のすべての `[[bin]]` で
   共有されるため、この変更後に再フラッシュすると littlefs に保存された
   設定がリセットされる。

両方を修正すると、アプリは起動してベイクしたアセットを問題なく
ロードする（1.44 MiB の音声 + 5.7 MiB の `fft_cache` で 1 008 ms、
PSRAM の余裕も十分 — ロード後 893 KiB 空き。モジュールドキュメントが
未解決のリスクとして挙げていた Vec+ベイク済みバイトのピーク合計
約 14.3 MiB に対する数値で、そのリスクは現実化しなかった）。
その後、PSRAM の問題にも実測のウォールクロック値にも到達する前に、
最初の FFT 呼び出しでパニックする — `coarse_sync` のスペクトログラム段の中である：

```text
esp-dsp FFT requires power-of-2 length ≥ 4 (got 7776)
```

`7776 = NSPS(3888) × NFFT_PER_SYMBOL_FACTOR(2)` —
`engine::sync::SyncDims::of::<Fst4s60>()` の coarse-sync スペクトログラム
FFT 長であり、`7776 = 2⁵ × 3⁵` は2のべき乗ではない。これは FT8 自身の
スペクトログラム FFT（`NSPS(1920) × 2 = 3840`、これも2のべき乗ではない）と
まったく同じ形で — だから FT8 は ESP-DSP バックエンドの2のべき乗専用
radix-2 カーネルを直接使う代わりに、`embedded-shared::esp_dsp_fft` に
手書きの `MixedRadix3840Fft` を持っている。FST4 には同等のものがなく、
7776 専用の2つ目が必要になる（さらに3つ目もおそらく必要：
`downsample_cached` の逆 FFT は `fft2_size = 6912 = 2⁸ × 27` で、これも
2のべき乗ではないが、`coarse_sync` が先にパニックするためまだ
到達していない）。

**つまり issue #306 の本来の問いへの答えは、まだ「スロットに収まるか」
ではない — 「組込みの FFT バックエンドは、FST4 の候補探索がデバイス上で
そもそも動くようになる前に、新しい非2のべき乗カーネルを必要とする」
である。** WSPR の `decimate_to_baseband` と違って、これは `esp-dsp` が
そもそも解決するはずのなかったサイズの問題ではない（WSPR の 1 474 560 点
スロット全体 FFT は設計上ホスト側でのベイクのまま）— 7776 点はシンボル
単位の FFT としては取るに足らない小ささで、ESP-DSP の asm カーネルが
サポートしないのは特に*基数*である。

**同日の2回目の試行：#307 のカーネルを先に作る代わりに、FFT の箇所を
そっくり迂回する。** `coarse_sync` と `downsample_cached` の FFT は
*sync/refine* 段にしかなく、LLR/BP/OSD 自体にはない — したがってホスト上で
既に refine 済みの候補（`process_candidate_basic_impl` の既存の
`precomputed_refine` パラメータが受け付けるのと同じ
`(cd0, freq_hz, i0, score)` の形）なら、#307 を待たずにデバイスが
両方をスキップできる。
`mfsk-core/tests/fst4_wsjtx_samples.rs::fst4_bake_golden_refined_candidates`
がこの方法で実際の（dedup 後の）候補をすべてベイクし、新しい
`engine::pipeline::process_candidate_precomputed`
（`internal-testing` ゲート付き、`process_candidate_basic` を踏襲）が
その継ぎ目を外部に公開する。クリーンにフラッシュ — そして再びパニック、
同じアサーション、今度は `got 36`：`GenericPipelineProtocol::snr_db` の
FST4 オーバーライド（`fst4_snr_db`）が `downsample_cached` を*3回目*、
独立に呼ぶことが判明した（`fst4_raw_cs` は正規化されていないスペクトルを
必要とし、既に正規化済みのベイクした `cd0` では代用できない）—
新しい `skip_snr` パラメータで閉じた（`P::snr_db` を呼ぶ代わりに
`DecodeResult::snr_db` に `NAN` を入れる。このベンチが測るのは
ウォールクロックであり、SNR の精度ではない）。再ビルド、再フラッシュ —
**3回目のパニック、同じアサーション、依然 `got 36`**：
`engine::llr::symbol_spectra`（LLR 抽出の実際の最初のステップで、
`precomputed_refine` に関係なくすべての候補で呼ばれる）が、
どちらの修正も触れていない自前の `ds_spb = NSPS/NDOWN` 点 FFT
（FST4-60A では 36）を計画している。

**3回目の試行：36 は本物の FFT がまったく不要なほど小さい。**
`ds_spb` は FST4 の全5サブモードで 36-42 である（`REFINE_STEPS` 自身の
ドキュメントコメントが既にこの範囲に触れていた）。素朴な O(N²) の
直接 DFT — 教科書どおりの定義であって近似ではない。どの FFT も
同一の和をより速い経路で計算しているにすぎないので — は、1回の呼び出しで
最大でも 42² = 1 764 回の複素乗加算で、それが供給する LLR/BP/OSD の
作業に比べれば無視できる。`embedded-shared::esp_dsp_fft::DirectDft`
として追加し、`EspDspPlanner::plan_forward` に、
`DIRECT_DFT_MAX_LEN = 64` までの任意の非2のべき乗長について配線した。
ホスト上で `numpy.fft`（`rustfft` が使うのと同じ非正規化の順方向規約）と
N=36 および N=42 で照合して検証済み、最大誤差は ~1e-6 — f32 レベルの
精度であり、符号/添字のバグはない。

3つの FFT 箇所をすべて閉じたことで（候補 refine をベイク、SNR をスキップ、
シンボルスペクトルの FFT を置換）、デバイス上のパスには FFT 呼び出しが
1つも残らない。（`DirectDft` を追加した後の）4回目のフラッシュ試行は
書き込みの途中で止まった — `espflash` の進捗バーが、消去後の全書き込みの
途中で進まなくなり、その後基板は `espflash board-info` に応答しなくなった。
無関係な USB/シリアルのハングと診断した（デバイスノードは存在し続け、
dmesg に USB の切断もなし）。コードのリグレッションではない — ユーザが
基板の電源を入れ直すとすぐに復帰し、それ以上の回復手順は不要だったことで
確認された。

**5回目の試行、今度は PSRAM。** 再ビルド、クリーンに再フラッシュ、
アセットは問題なくロード — その後、候補ループの中で
`memory allocation of 524288 bytes failed`。ベイクした両アセットが
まだ出荷されていた：`fft_cache`（5.7 MiB、*最初の*試行の修正
`fst4_bake_golden_precomputed` 由来）とベイク済み `cd0` バッファの
2.16 MiB で、ロード後の PSRAM 空きは 87 KiB しか残らず、ループ自身の
一時的な BP/OSD の確保が収まらなかった。`fft_cache` はこのパスでは
本当に死荷重だった — `precomputed_refine` がそれを読む唯一の呼び出し
（`downsample_cached`）をスキップし、`skip_snr = true` がもう一方
（`P::snr_db` 内の `fst4_raw_cs`）をスキップするので、一度も参照されず、
ただ領域を占めていただけである。ベンチから完全に外した
（`run_bench` はもうそれを取らない）。ロード後の PSRAM 空きは
87 KiB → 5.97 MiB になった。

**6回目の試行：完走、FST4 の組込みでの史上初のウォールクロック値。**
CoreS3 @ 240 MHz / `opt-level = 3`、シングルコア、パスのどこにも
FFT 呼び出しなし：

| | 値 |
|---|---:|
| 候補 | 41（dedup 後、生の `coarse_sync` 50 個中） |
| デコード | 2/2 — `CQ N5TM EL29`, `CQ K9KFR EN71`（ホストと完全一致） |
| 候補ループのウォールクロック | **89.691 s** |
| 同じ41候補に対するホストの `decode_loop` | 51.9 ms（`MFSK_TRACE_STAGE_FST4=1`、この環境） |
| デバイス/ホスト比 | **≈1728×** |
| FST4-60 のスロット後余裕 ~7 s に対して | **≈13× 超過** |

**単なる秒数ではなく、比率こそが発見である。** これは WSPR 自身の
*最初の*、完全に未最適化の測定（issue #260: ホスト基準 709.5 ms に対し
1214.3 s、≈1712× — `minsync2`、`opt-level=3`、160→240 MHz のクロック
修正という、その調査が最終的に見つけた最大の3つのレバーの前）に近い値に
なっている。この FST4 ベンチの
ビルドは、その3つのうち既に2つを備えており（`opt-level=3` とクロック
修正はどちらもビン単位ではなく `m5stack-cores3-app` 全体にかかる）—
したがって WSPR の生の最初の数値よりも有利な位置から出発していながら、
それでも同じ領域に着地した。この節の以前の文章（および
`embedded-shared::apps::fst4_bench` 自身のモジュールドキュメント）は、
FST4 の有界な LDPC/BP/OSD は「構造上安く失敗する」ので WSPR のような
専用のチューニングパスは要らないはずだ、という前提を繰り返しており、
それは明示的に *"an untested claim, not a measured one."* と注記されて
いた。今やそれは検証され、この未最適化の状態では成り立たない —
FST4 の LLR/BP/OSD パスの何かが、WSPR 自身の4ラウンドの最適化キャンペーン
の前の Fano 逐次探索と同程度の、実世界の候補1つあたりのコストを食っている。
未測定の容疑者が2つあり、ここではこれ以上診断していない：
`LLR_NSYM_MAX = 8` の階段のラング（グループあたり `4⁸ = 65536` 通りの
トーン組み合わせ仮説 — `fst4::decode` 自身の lazy-staircase コードはこれを
"128-256× FT8/FT4's own deepest rung" と呼んでいる）、そして、ここでの
FST4 は素の f32 汎用パイプラインを走らせており、FT8 の専用の
fixed-point `decode_block` や WSPR の今ではチューニング済みの
`decode_scan` と違って、組込み固有の最適化作業が*ゼロ*であること。

ついでに測ったピークスタック使用量：`BENCH_STACK` の 96 KiB という
当て推量は 95 064 B を未使用のまま残した — 実際に使われたのは約 3.2 KiB
だけで、`wspr_bench` 自身のスタックの歴史とは違って余裕は広い。

**7回目と8回目の試行：89.7 s は実際にどこへ行っているのか。**
候補ごとのウォールクロックのログを追加し（計測ループの最中ではなく後で
ダンプするので、UART の書き込みが数値を汚染しない）、ビルド時の
`MFSK_FST4_BENCH_DEPTH=bp_only` スイッチも追加した
（`DecodeDepth::BP_ONLY` 対デフォルトの `::FULL` — FST4 では両者は
`osd: bool` でのみ異なり、`LlrEffort` は適用されない — WSPR 自身の
issue #260 の対照実験と同じ形で、`confirmed = None` が `osd_decode` の前で
短絡する）。

89.4 s は41候補すべてに散らばってはいない。その 94% は6候補で、
そのすべてが失敗である：

| tier | 件数 | 1件あたり | 合計 | デコード |
|---|---:|---:|---:|---|
| nsync-gate fails | 33 | 50-177 ms | ~6 s | no |
| **the tail** | **6** | **13.8-14.2 s** | **84.2 s (94%)** | **no** |
| real signals | 2 | 54-58 ms | 0.1 s | **yes** |

実際のデコード2件はどちらも安い。コストのすべては、デコーダが最終的に
棄却する6候補にある — WSPR の issue #260 が見つけたのと同じ形だ
（"OSD ran 896 times and succeeded 0 times... the cost is not where any
of us was looking"）。

同じ41候補を OSD オフで再実行すると、そのテイルが分解される：

| | 合計 | テイル平均 | 割合 |
|---|---:|---:|---:|
| `FULL` (OSD on) | 89.411 s | 14.04 s | — |
| `BP_ONLY` (OSD off) | 51.755 s | 7.76 s | — |
| OSD の寄与 | 37.66 s | 6.28 s | **42%** |

OSD をオフにしてもデコードは両方成功する — このファイルの実信号は
どちらも OSD を必要としたことがない。つまり OSD は実際のコストだが、
過半ではない：**素の BP/LLR だけで 51.8 s、それだけで既に ~7 s の
予算を ≈7.4× 超過している。** OSD を削れば助かる（合計の 42%）が、それ
だけでは十分でない。

**9回目の試行：`LLR_NSYM_MAX = 8` という容疑者、確認され完全に局在化。**
`MFSK_FST4_BENCH_DEPTH=llr_probe` は `symbol_spectra` と各
`compute_llr_*` ステージを、BP/OSD なしで直接呼び、41候補すべてについて
各ステージを計時する（このモードは実パイプラインの nsync-gate による
早期離脱を意図的にスキップし、生存者だけでなくすべてのステージのコストを
同じ条件で比較する）：

| ステージ | 合計（41候補） | 割合 |
|---|---:|---:|
| `symbol_spectra` | 1.39 s | 0.5% |
| nsym=1 (`compute_llr_fast`) | 0.09 s | <0.1% |
| nsym=2 | 0.14 s | <0.1% |
| nsym=4 (`LLR_NSYM_MID`) | 1.10 s | 0.4% |
| **nsym=8 (`LLR_NSYM_MAX`)** | **301.2 s** | **99.1%** |

`nsym=8` だけで**候補1つあたり約 7.347 s**、どの候補でも 0.01% 以内で
一様である — 計算の規模（シンボルグループあたり `4⁸ = 65536` 通りの
トーン組み合わせ仮説）だけで決まる純関数で、データ依存ではない。この
1ステージが、`BP_ONLY` 実行のテイル約 7.76 s/候補の実質すべてを占める
（そのうち 0.034+0.002+0.003+0.027+7.347 ≈ 7.41 s。残りの約 0.35 s は
おそらく `decode_soft_pooled` 自身の BP 反復で、ここでは別個には測っていない）。

これが*変えない*ことが1つある：`SYNC_Q_MIN = 16` は既に FST4 自身の
`minsync2` 相当であり — WSJT-X 自身のラダー前ゲート
（`get_fst4_bitmetrics.f90`）を忠実に移植したもの（issue #197）— 実パイプラインで
41候補のうち33個がこのステージに到達するのを防いでいるのがそれである。
それを通過する8個は、実際の `jt9` が同じ計算を走らせなければならない
のと同じ母集団だ。WSPR の `minsync2` のギャップと違って、ここには
見つけるべき欠けた安価な棄却レバーはない — コストは、正当に深いデコードに
値する候補に本質的に付随するものであり、このコードベースが埋め損ねた
フィルタリングのギャップではない。

したがって残るレバーは `compute_llr_partial` 自体の内部（アルゴリズムの
再構成、fixed-point、SIMD/PIE）、FT8 の出荷構成が OSD を丸ごとスキップする
のと同じように組込みで `nsym=8` をスキップして recall のトレードオフを
受け入れること、あるいは並列化（デュアルコア）である。

**10回目の試行：それらのレバーの1つを引く。** `fill_bmet_for_nsym` の
コンパイル済み Xtensa 出力を逆アセンブルする
（ベンチ自身の ELF に対する `xtensa-esp32s3-elf-objdump`）と、そのホット
ループの2つの `f32::max()` 呼び出しが、それぞれ本物の `callx8 fmaxf` に
コンパイルされていた — Xtensa の FPU にはネイティブの float max/min 命令が
ないため、LLVM は `max` の IEEE-754 の NaN 伝播セマンティクスを単一の
比較には落とせない。`nsym=8` では候補1つあたり約 42 M 回のサブルーチン
呼び出し（2 呼び出し × 65536 要素 × 16 ビット位置）になり、42 M 回の
1サイクル比較ではない。

その呼び出し箇所の2つのオペランド（`v_for_one`/`v_for_zero`）は常に
`sqrt(re²+im²)`（有限、≥ 0）かリテラルの `f32::NEG_INFINITY` のどちらかで
— NaN にはならない — ので、`max` の NaN 処理はこの特定のループでは
死荷重であることが証明できる。素の `>` 比較に置き換えた
（NaN でない入力についてはビット同一 — 既存のすべての golden/AWGN
FT8/FT4/FST4 テストに照らして確認済みで、すべてバイト単位で不変）。
再逆アセンブルで修正を確認した：ホットループはネイティブの Xtensa の
`ule.s` 比較 + `bt`/`bf` 分岐にコンパイルされるようになり、そのループには
`callx8` がゼロ（関数の別の場所に `fmaxf` 呼び出しが1つ残っているのは、
ビット位置ごとに1回の正規化ステップのため — 2×65536×16 ではなく
16 呼び出し/グループで、無視できるとして放置した）。

同じ CoreS3、同じ golden、同じ41候補で測定：

| | 前 | 後 | 高速化 |
|---|---:|---:|---:|
| `nsym=8`（41候補 `llr_probe` 合計） | 301.2 s | 178.1 s | 1.69× |
| `nsym=4`（同上） | 1.10 s | 0.61 s | 1.80× |
| **`FULL` 候補ループ（実際の8候補の母集団）** | **89.411 s** | **71.312 s** | **1.25×** |

実デコードは依然 2/2 で、以前のすべての実行と同一である。本物の、
リスクゼロの、2行の勝利 — ただし `nsym=8` を単独で見たときに示唆される
~1.7× にはかなり届かず（ループのほかの要素ごとのコスト — 添字計算、
branchless-select のセットアップ、`s2` のトラフィック — は既にあって
手つかずのままなので、呼び出しだけを取り除いても、1反復に占める呼び出し
自身の割合より少ししか回収できない）、このセッションの最初の測定が
見つけた ~13× のギャップにはさらに遠く及ばない。

**11回目の試行：OSD 自身のアロケータのトラフィック — fmaxf 修正と同じ形を、
今や大きくなった側の半分に適用する。** LLR の修正後に `FULL`/`BP_ONLY` の
内訳を再集計すると、OSD は合計の 53% になっていた（42% から上昇 — LLR の
修正が分母を縮めたのであり、OSD 自体は手つかず）。
`osd_decode_generic::<Ldpc240_101Params>` — FST4 の OSD エントリポイントで、
FT8 の `Ldpc174_91Params` や MSK144 の `Ldpc128_90Params` と共有する
ジェネリックコード — は3次の組み合わせ探索である：FST4 では
`try_candidate` が1回の呼び出しあたり `C(101,3) ≈ 166 650` 回走り、
そのクロージャは*毎回*新しいヒープ `Vec<u8>` を2つ（240 B + 101 B）確保し、
CRC 検証が失敗する圧倒的に一般的なパスで直ちに解放していた。逆アセンブルが

**12回目の試行：両側に1つずつレバー — LLR 側は VK3NV の `bit_sel` の
ブロック縮約、OSD 側は `verify` ゲートを自身の O(n) スキャッタの前に並べ替える。**

*LLR 側。* VK3NV（issue #306）は、`fmaxf` 修正後でも
`fill_bmet_for_nsym` の内側ループには要素ごとにシフト1つ、マスク1つ、
branchless select 2つが残っていること、そして固定の `bit_sel = b` では
`(i >> b) & 1` はまったくデータ依存ではなく、`2^b` 個のゼロと `2^b` 個の
1が繰り返される既知の周期パターンであることを指摘した。
`nt = ntones^nsym` は常に2のべき乗（どのプロトコルの `ntones` もそう）なので、
`block = 2^bit_sel` は常に `nt` を割り切る — ループは代わりに `s2` を
`2^bit_sel` 個ずつの連続ブロックで歩き、各ブロックがどちらのアキュムレータ
（`mo`/`mz`）に入るかを交互にでき、要素ごとの比較は1回、要素ごとの
述語機構はまったく不要になる。要素の訪問回数は以前と同じ（`bit_sel` ごとに
`nt`）で、要素ごとのオーバーヘッドだけが崩れる。FT8、FT4、FST4、MSK144 の
共有コードパスにわたってホスト上でビット同一 — このループは3つすべてが
使う。

*OSD 側。* `try_and_update` のスキャッタ（`c[perm[col]] = cp[col]`、
`O(n)=240`）は、約 166 650 回の呼び出しの*すべて*で、そのほぼすべてを
棄却する `verify`（CRC 型）ゲートより前に走っていた — スキャッタの目的は
`verify` が検査する `decoded = c[..k]` を作ることだが、最初の `k` ビットを
得るために `n` 長の符号語全体を組み立てる必要はない：逆置換
（`inv_perm[perm[col]] = col`、1回だけ計算）があれば
`decoded[i] = cp[inv_perm[i]]` を `O(k)=101` で直接集められ、`O(n)` の
完全なスキャッタは実際に `verify` を通るまれな候補まで先送りできる。
別に、重み付き距離のループ（同じまれな通過にだけ到達する）は、
`perm`/`llr` が候補間で変わらないにもかかわらず、`llr[perm[col]] > 0.0` と
`.abs()` を毎回ゼロから再計算していた — 代わりに `hdec_perm`/`absrx_perm` を
1回だけ事前計算した。両方の変更は、FT8（full-parity 8/8、ship-config）、
MSK144、FST4-60、および435テストのライブラリスイート全体にわたって
ホスト上でビット同一。
再逆アセンブル：`osd_decode_generic` のクロージャは以前の 4.2 KiB から
約 450 バイトに縮み、スキャッタ/重み付き距離のコードは、その前で無条件に
走るのではなく `verify` 呼び出しの背後に明確にゲートされている。

実デコード 2/2 は不変（`CQ N5TM EL29`, `CQ K9KFR EN71`）。

**13回目の試行：`osd_decode_generic` の XOR 構築のビットパッキング —
上記の `verify` ゲートの並べ替えでは届かなかった、無条件の `O(n)`
ステップ。** その並べ替えはスキャッタをまれな `verify` 通過候補まで
先送りしたが、符号語の*構築*そのもの（`c1[col] ^= g[k1*n+col]`、および
`c2`/`c3`/`c4` についても同様）は同じ方法では先送りできない — それは
候補を消費しているのではなく、それ*が*候補であり、約 166 650 通りの
3次の組み合わせのすべてで無条件に走る。ただしスキャッタと違って、ここには
置換が関与しない：`c*` も `g` の行も既に同じ置換済み列順になっているので、
これは同じ長さの2つのバイト配列の素の要素ごとの XOR であり —
`osd_setup_generic_packed` がガウス消去中の自前の行 XOR のために既に
ビットパックしている形とまったく同じである（同じファイル、同じ理屈、
既に本番投入済み）。`g`（`osd_setup_generic_packed` が返すとおりの
1ビット1バイト。その関数自身の戻り値の型は
`packed_setup_differential` のテストが1ビット1バイトの参照実装と照合
しているので手を付けない）を、`osd_decode_generic` の呼び出しごとに1回
（`O(k·n)`、無視できる）、1行あたり `OSD_WORDS = 4` 個の `u64` ワードに
詰め直すと、`c1`/`c2`/`c3`/`c4` の各構築は 240 バイトのコピー + 240 バイトの
XOR ループから、4回のワード XOR になる — 各々が今や
`parent ^ g_packed[row]` として直接計算されるので、コピーはまったく不要。

`try_and_update` もパック表現に移る：`O(k)` の gather
（`decoded[i] = cp[inv_perm[i]]`）はバイトのロードの代わりにビット抽出
（`(cp[idx/64] >> (idx%64)) & 1`）になる — 漸近コストは同じで、ロード1つが
シフト+マスクに置き換わる — そしてスキャッタ + 重み付き距離のループ
（依然 `O(n)`、依然として以前とまったく同様に `verify` の背後にゲートされる）は、
どちらも列ごとの同じビット抽出を必要とするため、2パスから1パスにまとまった。
ホスト上でビット同一：FT8（full-parity 8/8、ship-config）、MSK144、FST4-60、
435テストのライブラリスイート全体、そして `fixed-point` feature も
スポットチェック済み（`ft8_qso3_apoff_recall` の床は不変）。

関連する副次調査で、このセッション自身の `osd_decode_generic` の逆アセンブル
作業に促されたもの：`osd_decode_deep4` の `k4_limit` パラメータは、
4次の追加のフリップを*最も*信頼度の低い MRB ビット
（"errors concentrate in low-|LLR| bits"）に制限するものとして
文書化されているが、経験的には（`osd_setup_generic_packed` を通した
合成の単調 LLR プローブによれば）行添字 `0..k` は*最も*信頼できる
（行 0）から*最も*信頼できない（行 `k-1`）へ走る — つまり出荷されている
`0..k4_limit` の範囲は最も信頼できる側の端であり、ドキュメントコメントが
述べる意図とは逆である。両方向を直接試すため、`osd_decode_generic` に
`k4_tail: bool` パラメータを追加した（既存のすべての箇所で `false`、
ビット同一）。修正を追う前に本番への影響をたどった：`osd_decode_deep4` は
実質 FT4 専用である（FT8 自前のエンジンは代わりに WSJT-X 忠実な
`osd_decode_npre1(_npre2)` を使い、このコードパスには一切触れない —
`ft8/decode.rs` の3つの呼び出し箇所はすべて `#[cfg(test)]` の内側にある）。
そして FT4 自身の `osd_depth3_min` ゲート（`nsync ≥ 14/16`）は、
クリーンな AWGN では BP+depth-2/3 の失敗を構造上まったく通さないことが
分かった — m14 から m22 までスイープし（各20トライアル、golden の周波数
付近の候補）、方向の問題はさておき、実際の depth-4 ゲートに到達する候補が
ゼロだったことを確認した。方向の食い違いは本物だが、現時点では休眠
状態にある — 将来の変更（より緩いゲート、CCIR フェージング、新しい
呼び出し側）が実際にそれを走らせうる場合に備えて記録した。

`OSD_MAX_N` 境界付き固定配列のイディオムを通じて任意の `LdpcParams` に
一般化する（`ntheta`/`ntau` は実行時パラメータ — WSJT-X はそれらを
プロトコルごと*かつ* `ndeep` ごとにチューニングしているため、トレイト定数
としては収まらない）。FST4 の OSD ディスパッチに `ndeep=2`
（`ntheta=12`、`npre1` のみ）と `ndeep=3`（`+ntau=14`、`npre1+npre2`）で
配線した — FST4 の本番コードが要求するのはこの2つの深さだけである。

置き換えるものとビット厳密には一致しない（本当に異なる探索戦略）ので、
recall は差分テストではなく独自の確認が必要だった。最初の AWGN 比較
（m26/m27、各100トライアル）を*以前の、構成の異なる*診断パイプラインの
ベースラインに対して行うと、m27 で7ポイントのリグレッションがあるように
誤って見えた — 信用する前に気づいた：新しい `internal-testing` 専用の
診断オーバーライド（`fst4_osd_diag_force_old`）が、*まったく同じ*本番の
エントリポイントを同じ200トライアルで両方のアルゴリズムに通し直し、
統制された A/B にした。結果：m26 で 96/100 対 96/100、m27 で 71/100 対
70/100 — 測定可能な recall コストはなし。（以前の「リグレッション」は
りんごとみかんの比較になったベースラインであって、本物の発見ではなかった —
詳細はこの issue の GitHub スレッドを参照。）

実際の CoreS3 ハードウェアで、同じベイク済みの41候補について、
OSD アルゴリズムだけを変数として測定：

| | 旧（組み合わせ） | 新（npre1/npre2） | 高速化 |
|---|---:|---:|---:|
| **`full`** (nsym=8+OSD) | 54.087 s | **43.134 s** | 1.25× |
| **`no8_osd`** | 25.710 s | **17.147 s** | 1.50× |

実デコード 2/2 は両構成で不変。**元の 89.411 s のベースラインからの累積：
`full` は 2.07×（~7 s の予算に対して ≈6.16× 超過）、`no8_osd` は 5.21×
（予算の ≈2.45× 超過）** — これまでで最良の `no8_osd` の数値であり、
npre1/npre2 の移植が「より大きな潜在的性能レバーに見える」という VK3NV
自身の読みを裏付ける。デュアルコアの見込みもそれに応じて改善する：
`no8_osd` の 17.147 s ÷ WSPR の実測デュアルコア効果 1.35–1.47× は
11.7–12.7 s（依然予算超過）；楽観的な 2.0× の上限では 8.57 s に達し —
7 s に近いが、まだ下回ってはいない。

**注意点、同日に CCIR-moderate フェージングへ確認を広げて判明：** 上記の
「測定可能な recall コストなし」という判定は AWGN に限定されたもので、
一般的ではない。同一パイプラインでの新旧比較（SNR あたり 100 トライアル、
`fst4_osd_diag_force_old`）を CCIR-moderate で行うと、m23 から m26 にかけて
AWGN には見られない本物の、拡大する低下があった（`full`：m26 で 24→18、
-25%；`no8_osd`：23→18、-22%）（AWGN では m26 は同点、m27 は1トライアル以内）。
OSD を一切呼ばない構成 `bp_only`/`no8_no_osd` はどの SNR でも新旧で
バイト同一であり、原因は OSD アルゴリズム自体に切り分けられる。
具体的な旧方式のみのトライアルで根本原因を特定した：枝刈りなしの
組み合わせ探索は本物の3次の符号語（`hard_errors=55/240`、深刻な
フェージングによる劣化と整合する）を見つけるが、`npre1+npre2` は
見逃す。移植のバグではない — WSJT-X 自身の `npre2` ハッシュ表が
表面化させるのは、部分パリティのシグネチャが `ntau` ビット窓の内側で
別の MRB ペアと衝突する重み3のパターンだけで、可能なすべての重み3の
組み合わせではない。AWGN ではこれはめったに問題にならない（誤りは
低 |LLR| ビットに集中し、`npre1`/`npre2` の想定と合致する）が、深くフェード
した単一のシンボルは、その想定が覆わない誤りの幾何を生みうる。
#306/#198 に記録した。まだ対処はしていない。

**16回目の試行：npre1/npre2 ビルドでの新たな `FULL`/`BP_ONLY` の時間内訳
（VK3NV の依頼 — 「いまボトルネックはどこにあるか」）。** `BP_ONLY` は
OSD をまったく呼ばないので移植の影響を受けない；それでも、移植前の測定を
再利用する代わりに同一ビルドの数値のために再フラッシュした。上の
15回目の試行の `full`：

| | 時間 | `full` に占める割合 |
|---|---:|---:|
| `BP_ONLY`（LLR/BP のみ） | 31.023 s | 71.9% |
| `full` − `BP_ONLY`（OSD、推定） | 12.111 s | 28.1% |
| `full`（両方） | 43.134 s | 100% |

移植前の内訳（`old full` 54.087 s − 同じ 31.023 s の `BP_ONLY` = 23.064 s が
OSD、42.6%）と比べると：OSD の*絶対*コストは 1.90× 下がり
（23.064 s → 12.111 s）、その*割合*は 42.6% から 28.1% に下がった —
ボトルネックは、移植が手を付けなかった BP/LLR 側に戻った。
`BP_ONLY` 自身の残りのコスト（31.023 s）は、それだけで依然として ~7 s の
予算の ~4.4× 超過である — 次の量的に意味のあるレバーは、もしあるなら、
OSD ではなく内訳のその側にある。

**17回目の試行：rung-major スケジューリング + 本物の `llrd` アブレーション
（issue #306 項目3、VK3NV）。** VK3NV の提案：候補ごとではなくラングごとに
スケジュールする — どの候補の `nsym=2` よりも先に、すべての候補の
`nsym=1` を試し、以下同様 — ことで、締切に制約された組込み受信機が、
候補リストのどこに位置するかに頼らず、簡単なデコードをほぼ即座に報告
できるようにする。2段階の計画：(1) ホスト側の正しさの確認 + ホストの
計時から投影した anytime 曲線、(2) 本物の実装 + 実機での測定。

ステップ1で、その概念が成り立つことが分かった：実際の FST4-60 golden
録音では、実際の候補順序がたまたま2つの実デコードを先頭に置く（幸運 —
depth-first ではそれらを ~0.15s/0.30s でデコードする）が、最悪ケースの
並べ替え（デコードされる2候補を最後に移す）では depth-first は
合計 30.15s のうち ~30.0s/30.2s に押しやられる一方、rung-major は順序に
かかわらず最初のデコードまでの時間を ~7.4s に抑える（どちらでも総作業量は
同じで、並べ替えが*何が*デコードされるかではなく*いつ*かだけを変える
ことを確認する）。

本格的な rung-major 実装に踏み切る前に、ステージのアブレーション
（`fst4_60_diag_stage_ablation`/`_ccir_moderate`、クロッシング付近で
SNR あたり 100 トライアル）が、本番の BP/OSD の6ステージ（`llra`、`llrb`、
`llre`/mid、`llrc`/max、`llrd`、そして5つすべてに対する OSD）のすべてが
そもそもスケジュールする価値があるかを問うた：**`llrd`（正規化された
nsym=1 バリアントで、本番では*最後に*試される）は、追加の recall を
ちょうどゼロしかもたらさない**。AWGN でも CCIR-moderate でも、試験した
あらゆる構成で（あり/なしでヒット数がバイト同一）。rung-major 固有の
簡略化ではなく — ユーザの枠組みによれば、このプロトコルに対する本物の
5ステージ設計である：このパイプラインは特に組込みの FST4 に仕えるので、
`engine::pipeline::process_candidate_basic_impl` のプロトコル横断的な
ジェネリック性を保つ必要はない。

ステップ2：`fst4::rung_major::decode_rung_major<P>` — 本物の、ホストで
テスト済みの、FST4 固有の関数（FT4/FT8/FST4/MSK144 では手つかずのままの
共有 `process_candidate_basic_impl` には組み込まない）。5ステージ、`llrd` は
落とし、`skip_llrc` は既存の `no8_osd` のトレードオフを踏襲。検証で、
どの数値も信用する前に本物のバグが見つかった：最初のバージョンは、
`process_candidate_basic_impl` 自身の `try_position` クロージャが適用する
周波数補正（`df_hz = refined_freq_hz - cand.freq_hz` での
`freq_shift_cd0`）をまったく適用しなかった — `RungMajorCandidate` が
粗い周波数と refine 済みの周波数を1つのフィールドに混同しており、
`df_hz` を黙ってゼロにして、この演習全体が狙っているまさに境界的な
候補の同期をずらしていた。最初の実機の合計（12.500 s）が、既知の
43.134 s のベースラインに対して不自然によく見えたことから表面化した；
実際にベイクした組込みアセットに対する nsync ゲート通過候補数の直接の
確認では、期待された6個ではなく41個中4個しかゲートを通っておらず、本物の
アルゴリズム上の勝利ではなくバグであることを裏付けた — 修正すると、
期待された6つの難しい候補が再び現れ、ステージごとの計時も妥当になった。

**訂正後の実機測定**（同じベイク済みの41候補、`llrd` を落とし、
`skip_llrc` のみが他の変数）：

| | 6ステージ（本番の形） | 5ステージ（`decode_rung_major`） | 高速化 |
|---|---:|---:|---:|
| `full` | 43.134 s | **40.102 s** | 1.08× |
| `no8_osd` | 17.147 s | **13.643 s** | 1.26× |

実デコード 2/2 は不変。**89.411 s のベースラインからの累積：`no8_osd` は
今 6.55×、~7 s の予算に対して ≈1.95× 超過** — この調査が生んだ最良の
数値。デュアルコアの見込み：13.643 s ÷ WSPR の実測効果 1.35–1.47× は
9.28–10.1 s（依然予算超過）；楽観的な 2.0× の上限では **6.82 s — この調査で
初めて 7 s の目標を下回る**、ただしそれはその上限においてのみで、
実測のデュアルコア効果ではない。

rung-major スケジューリングそのもの（`llrd` のアブレーションとは別の、
順序の性質）は、まだ実機で単独には測定されていない —
`decode_rung_major` は構成上ステージを rung-major の順序で実行するが、
このセッションの上記の実機の数値が測るのはその*合計*であって、ホストの
投影がやったような depth-first 対 rung-major のレイテンシ比較をデバイス上で
行ったものではない。公平なデバイス上の A/B には、同じ5ステージ集合で
組んだ depth-first の対照が必要になる — 今回は行わなかった。

**18回目の試行：issue #308 の `i0` ジッタのリトライ — 固定ポリシーでは
なく呼び出し側の選択にした。** #308 がホストに入った同じ日
（FST4 の候補は `i0 ∈ {refined, +1, -1}` でリトライされるようになり、
WSJT-X の `fst4_decode.f90` に一致する）、それは `decode_rung_major` にも
移植された — 両者が同じ `symbol_spectra`/BP/OSD の構成要素を通るので
単純だった。実機の測定で、無条件に適用するとコストが recall の利得に対して
不釣り合いであることが分かった：`full` 40.102 s → **121.281 s**（3.02×）、
`no8_osd` 13.643 s → **34.200 s**（2.51×）に対し、確認した SNR での
recall の利得はわずか数ポイントだった
（`fst4_60_diag_i0_offset_ablation`：AWGN m27 74→82/100、CCIR-moderate
m26 18→23/100 — 本物だが、2-3× のコストに見合う比率ではない）。
2つのオフセットを個別にアブレーションすると、どちらも `llrd` のように
きれいにタダで切れるものではなかった：`{0,-1}` だけで組み合わせた利得の
大半が得られる（AWGN m27 79/100、CCIR-moderate m26 21/100）が、それでも
簡易なホストの計時（`fst4_60_diag_i0_offset_host_timing`）で本物の 1.84× の
コストがかかり、`{0,+1}` は得られる利得が小さいうえコストはほぼ同じである。

mfsk-core が1つの答えを選ぶのではなく、`decode_rung_major` は
`offsets: &[i32]` を明示的な呼び出し側のパラメータとして公開する —
既存の `skip_llrc`/`skip_osd` の選択と同じ形。スロットをまたぐことを
許容できる監視型の運用は、スロットごとに厳格な締切がある運用とは
コスト/recall のトレードオフがまったく異なるので、これは
デコーダの決定ではなく、運用形態の決定である。2引数の `decode_rung_major`
ラッパーは締切優先のデフォルトとして `&[0]` を保つ（`no8_osd`：13.643 s、
~7 s の予算に対して ≈1.95× 超過、17回目の試行が締めくくったのと同じ数値）；
`&[0, -1]` と `&[0, 1, -1]` は、より多くの recall を求めて時間を使える
呼び出し側のために用意されており、上記のコスト/recall の数値は再導出を
要さず既に測定済みである。ホスト（`process_candidate_basic_impl`、
issue #308、無条件の `i0±1`）と組込みの*デフォルト*が乖離したままで
あることは引き続き許容される — WSJT-X 忠実性と組込みの厳格な締切は
別の問いである — が、ある運用がそれを賄えるなら、組込みはもはや
忠実性の修正から締め出されてはいない。
