### Matching dbg4 source log received

The user copied the new log to the NAS under its original `rsp_clock.log`
name. It was copied into the capture directory and parsed: 11,131 C records
and 11,131 F records over 600.2 seconds. There are **2,107 positive sample
number gaps totaling 22,712,714 samples**, with maximum gap 38,004 samples.
The cumulative filled count remains zero, as expected for plain mode.

Discarding the first 30 seconds gives:

- Source callback payload: 978,535 S/s, agreeing with the client-side
  978,656 S/s within the different observation boundaries.
- 2,020 positive gaps totaling 21,627,122 samples (21.12 nominal seconds).
- Three post-startup reset records, at source-relative times 106.760,
  334.237 and 439.844 s. Their preceding C-record intervals last 1.435,
  1.432 and 1.426 seconds, matching the three long client delivery pauses.
- Excluding those reset intervals, received samples plus numbered missing
  samples account for 1,024,100 S/s, approximately +98 ppm from requested.
  This is a finite-window accounting check, not a precision ADC calibration.

This establishes that the steady shortfall is largely **numbered missing
source samples**, not simply a uniformly slow ADC clock. Zero filling can
preserve the positions of these identified holes. However, dbg4 invalidates
the numbering comparison at a reset, so `-Z` does not by itself identify or
repair the roughly 1.4-second recovery interruptions.

## Client correction on recorded IQ (2026-10-16 JST)

The user clarified that normal, unmodified servers are the deployment target.
Server changes are diagnostic controls only; the bulk/fill hardware sequence
was stopped. All subsequent signal verification uses the two saved recordings,
not a connection to the radio. The historical `4d3f1ac4` client was also built
and replayed against the 245-second recording: it recovered no messages there.
Its older published result used a different recording and is not a positive
control for these captures.

### Frequency translation and payload timing were coupled incorrectly

The startup measurement lowered the receiver's nominal rate to approximately
987 kS/s and also used it for RF mixing. The ADC still sampled at approximately
1.024 MS/s; missing samples lowered throughput instead. At the 7.074 MHz channel,
58 kHz above the IQ centre, this displaced the wanted signals by over 2 kHz.

The client now pins frequency translation to the requested ADC rate and uses
payload throughput only for the approximate audio/UTC correction. Direct and
PFB channelizers support the separate acquisition-clock offset. Completed slots
carry the RF/audio frequency scale; decoded RF frequencies and waterfall axes
are transformed about the front end's **3000 Hz** audio centre. Retunes, gaps,
and payload-rate updates preserve the separate acquisition clock.

The GUI exposes **Rate model → Sample loss (nominal ADC clock)**, the new default.
**ADC clock offset** preserves the former coupled model for a source whose ADC
clock actually differs. CLI equivalent: `--rtl-adc-clock-offset`. The stock
socket fixture that genuinely changes the ADC rate explicitly selects that model.
Neither model reconstructs the positions of unknown deleted samples.

### Paired, faster-than-real-time replay

`recorded_iq::decode_recorded_iq` feeds the real receiver, stream loop and decoder
workers from `record.py` bytes and recorded arrival times. It waits for workers
instead of losing slots to accelerated replay. No source counter log is used by
the decoding path. Both conditions have identical start/end bounds and rate
tracking; only the pinned acquisition clock changes.

The fixed initial payload rates, 986,607.500 and 987,785.406 S/s respectively,
were least-squares estimates from each recording's first 10–40 seconds using
the same 16,384-IQ grouping as the real client. Decoding starts at 40 seconds,
so these estimates use no later samples. They were not tuned for decode count.

| Recording and decoded bounds | Former frequency model | Nominal ADC frequency model | Nominal ADC + explicit pause-loss inference |
|---|---:|---:|---:|
| 245 s recording, 40–240 s | 0 rows | 10 rows, 1 reanchor | 10 rows, 0 reanchors |
| 600 s recording, 40–599 s | 1 row | 28 rows, 3 reanchors | 32 rows, 0 reanchors |

With pause inference, the 600-second recording's decoded DT range is -0.570 to
+0.155 s; the 245-second recording's range is -0.335 to +1.080 s. These are
off-air senders with unknown individual timing, not synthetic DT ground truth.
The positive one-second DT of a repeatedly heard station cannot simply be
treated as receiver bias. Counts are observations on these recordings, not a
general recovery guarantee.

The existing pause heuristic remains **off by default**, since a buffered source
that later delivers everything can be harmed by inferred loss. It is enabled
only in the final GUI test profile for these recordings with sample loss and
long recovery pauses. The client itself still uses no source counters.

### GUI replay and NTP

`replay_rtltcp` serves the saved 8-bit IQ at the original relative arrival times.
Its own UTC and the GUI's UTC are independently synchronized to `ntp.nict.jp`
using the application's clock module, without changing OS clocks. Each replay
starts on the recording's original 15-second phase, mapped to current UTC.
The sender logs the scheduled UTC and its NTP correction; failed initial NTP
synchronization stops the sender rather than silently using the PC clock.

The first full GUI replay, with the new frequency model and pause inference off,
recovered 9 SQLite rows and logged one +1.355 s reanchor. The sender's correction
was +47 ms (9 ms RTT) and the GUI's +51 ms (8 ms RTT); its largest replay send
lateness was 13.424 ms. Queue loss remained zero. Repeated UA0LQE rows returned
to approximately 7.075533–7.075534 MHz, consistent with the nominal-rate signal
position rather than the former shifted passband.

The final GUI profile enables pause inference and is separate from the original
user settings: `/tmp/mfsk-recorded-gui-loss/settings.json`, with SQLite and
STATUS.log beside it. The preceding inference-off GUI run is preserved under
`/tmp/mfsk-recorded-gui-fixed/`. Both use only `127.0.0.1:5150`.

The recordings did **not** save the capture PC's original NTP correction.
Current sender/receiver clocks are aligned, but the original absolute acquisition
UTC and absolute DT cannot be retroactively certified. Relative timing and
paired comparisons remain meaningful. A fixed pipeline delay was not guessed
from these unknown transmitters.
