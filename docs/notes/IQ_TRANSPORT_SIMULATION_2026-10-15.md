# IQ 取得レート・固定遅延・API 欠落のシミュレーション（2026-10-15）

## 結論

このモデルで最優先に直すべきものは、欠落によって失われる**サンプル位置**である。欠落位置をゼロ埋めし、真の取得レート差がある場合だけその差を補正し、固定遅延を受信時刻から引けば、既存の FT8 デコーダで弱信号の復号まで回復した。デコーダの同期・FEC 閾値は変更していない。

平均到着レートは真の取得レートとは限らない。一定の欠落なら平均レートで伸ばす方式にも救済効果があるが、周波数が約930 Hzずれた。欠落量を変動させると −18 dB で0/18件となった。同じ変動をゼロ埋めすれば18/18件だった。

公称レート条件の診断設定に既定の校正値が残っていたため、`rtl_calibrate = 0` を明示して全330実行を再試験した。本表・CSVは修正後の値。実GUIの測定値はこの診断設定の影響を受けない。確率的な欠落の追加検証は [別報告](IQ_STOCHASTIC_LOSS_2026-10-15.md)。

## 測定方法

- 55条件 × SNR −10 / −18 dB × 雑音3系列、330実行。各実行の共通評価区間は信号源の45〜135秒、6送信。評価対象は計1980スロット。同一雑音系列を条件間で共有する対照比較であり、1980独立試行ではない。
- 仮想時刻の試験は `skimmer-core` の実際の `receiver` / `stream_inner` / 復号 worker / `settle` を通す。実ソケット、GUI、OS スケジューラを省き、取得 UTC と配送 UTC を別々に与える。ライブラリ内部の時刻追従・レート推定・gap 推定は実装そのもの。
- 指定レート192 kS/s、IQ 中心はダイヤルの25 kHz下、音声1500 Hz。6種類のCQを15秒ごとに変え、復号 UTC と発生 UTC を対応付ける。同期時刻に正常な .5秒プリロールを置いた12.64秒の FT8 波形。16-bit IQ、独立成分の白色 Gaussian 雑音、SNR は2500 Hz基準。
- 真の取得 Fs が1.7%低いケースと、取得 Fs は公称どおりで欠落により配送量だけ減るケースを分離した。**実機の ADC が1.7%低いと実証したわけではない。** −1.7%は二つの原因を区別するための仮定。
- 欠落の主条件は65 ms / 1.85 s（約3.51%）。API の配送停止は90 ms。固定遅延は0 / 250 / 750 / 1500 / 3000 / 15000 ms。配送はFIFOで、最後の取得サンプルの時刻以降にしか到着しない。
- 変動条件は欠落長が10秒ごとに19.5 / 65 / 110.5 ms、周期1.85秒。欠落率は約1.05 / 3.51 / 5.97%。API 停止長も欠落長＋25 msへ変える。取得 Fs はその間一定。
- 平均到着レート補正は最初の30秒を実際に読み捨てて `RateMeter` で測定し、`plannable_rate` とレート tracker を使う通常の校正経路。真の Fs 補正はその Fs を既知とする診断用上限。固定遅延補正も既知の注入量を差し引く。信号源の UTC をデコーダへ直接渡してはいない。
- worker のキューあふれは全330実行で0。通常スロットの比較では early decode を無効にし、最後に worker を待って集計する。後述の GUI 試験では early decode と waterfall を有効にした。

**判定を分離した。** 「復号」は正解メッセージを回収した数。「時刻・周波数も正しい」はさらに、発生元スロットUTCが一致、周波数誤差≤2 Hz、abs(DT)≤50 ms。後者は診断用の厳しい条件であり、復号自体の必要条件ではない。固定遅延750 msで DTが+.75 sでも復号はできる。

## 何がデコーダを壊すか

### 1. 真の取得レートと仮定レートの差

欠落がない場合、デコーダが仮定するレートを `F_rx`、実取得レートを `F_adc`、IQ中心からダイヤルまでを `C` とすると、音声周波数の誤差は次になる。

```text
Δf = (C + f_audio) × (F_rx / F_adc − 1)
F_adc = 0.983 F_rx、C = 25000 Hz、f_audio = 1500 Hz
Δf ≈ +458.8 Hz
```

実測中央値も約+459 Hz。12.64秒の送信は音声上で約215 ms短くなる。UTCアンカーを追わせても、波形内部のシンボル間隔と周波数変換は直らない。時刻追従だけを5%に拡大しても −18 dB は1/18件、取得 Fs 補正は18/18件。

### 2. API 欠落を真のレート差と取り違える

サンプル位置が削除されると、欠落率pに対して配送レートは概ね `F_payload = F_adc × (1−p)` となる。これは ADC のサンプリング周期が変わったという意味ではない。

```text
65 ms / 1.85 s ≈ 3.51%
12.64秒中の時間圧縮 ≈ 444 ms（約2.8 FT8シンボル相当）
平均配送 Fs でリサンプルした、欠落のない区間の周波数誤差
Δf ≈ −p × (C + f_audio) ≈ −931 Hz
```

シミュレーションでは約−932 Hz、GUIでは−930〜−933 Hzを観測。平均伸長は全体の長さを近付けても、どのシンボルの途中が削除されたか、そこで飛んだ位相を元に戻せない。一定欠落なら −18 dB でも15/18件回収するが、削除量が変動すると0/18件。

ゼロ埋めは欠落信号を復元しないが、欠落を時間圧縮から「その位置の情報消失」に変える。NCOとリサンプラのサンプル番号が保たれ、受信された部分の位相・周波数・シンボル位置が正しくなる。LDPCが残った情報で復号できた。

### 3. 固定遅延はレートの問題ではない

固定遅延 D を補償しない場合、到着時刻由来の IQ 時刻は概ね `取得UTC + D`。波形の周波数・シンボル周期は変わらない。250 / 750 / 1500 msは18/18件復号するが、DTにその遅延が残る。3秒では0/18件、補償すると18/18件。

FT8の標準 coarse sync の lag 探索は±2.5秒（`ft8/decode_block/coarse_sync.rs`）。3秒は探索範囲を越え、15秒スロットの末尾も切れる。探索幅の拡大だけでは取得UTCを復元できない。15秒の固定遅延では全件復号するが、すべてスロットUTCが15秒ずれた。繰り返す同じメッセージの件数だけではこの誤りを見逃す。

`rtl_tcp`には取得UTCが含まれないため、到着だけから未知の一定遅延と信号源のDTを一意に分けることはできない。今回は注入した遅延を既知として補償した。実機では測定したパイプライン遅延、取得タイムスタンプ、既知時刻の基準信号などが必要。

### 4. 遅い配送を欠落と判断すると新たな損失を作る

750 msのAPIバッファ停止でも全サンプルが後送されれば、公称Fs経路は18/18件を正しい時刻・周波数で復号した。現在の校正fallbackは500 msを超える到着間隔から `rx.gap()` を推定する。これを有効にすると、各系列で4回、合計12回の偽gapが入り、−10 dBで9/18件、−18 dBで9/18件へ減った。推定Fsの短期バイアスもあり、周波数中央値は約+42 Hzで、DTにも数百msの誤差が残った。

「キャリブレーション有効」と「長い配送停止は欠落と仮定」を同じ条件で切り替えている点は、後送があるサーバには不適切。到着間隔だけでは、後で届くサンプルと本当に失われたサンプルを識別できない。

## どこまで損失を減らせば復号に至るか

取得Fsは正しいまま、欠落を削除し、周期1.85秒を固定して長さを減らした結果。すべて−18 dB、各18送信。

| 削除長 | 欠落率 | 復号 | 時刻・周波数も正しい | DT 範囲 |
|---|---:|---:|---:|---|
| 65 ms | 3.514% | 0/18 | 0/18 | — |
| 40 ms | 2.162% | 0/18 | 0/18 | — |
| 20 ms | 1.081% | 7/18 | 0/18 | -0.845〜-0.155 s |
| 10 ms | 0.541% | 16/18 | 0/18 | -0.635〜-0.245 s |
| 5 ms | 0.270% | 18/18 | 0/18 | -0.280〜-0.110 s |
| 1 ms | 0.054% | 18/18 | 18/18 | -0.015〜-0.005 s |

この条件では削除を65→20 msへ減らすと一部の復号に至り、5 msでは全件回収した。ただしDTは−.110〜−.280 sへずれた。1 msでは全件かつDT−5〜−15 msになった。これは選んだ周波数・欠落位相・送信長の結果であり、1 msを一般的な安全限界とはしない。少量でも残った欠落は累積し、長時間の時刻精度を保証しない。

位置を保つゼロ埋めは、3.5%欠落で連続長20 / 65 / 120 / 240 / 400 / 640 msでは18/18件。1000 msでは12/18件で、3系列合計12回の時刻reanchorが発生した。これも選んだ欠落位置に限る。65 msのゼロ埋めで欠落率を7 / 14 / 28%へ上げると、−18 dBで18 / 18 / 17件。ゼロ埋めが情報を復元するわけではなく、FECの余裕が尽きれば復号できなくなる。

開始位相を1.05→.25 / .75秒へ変えた65 msゼロ埋めも18/18件。ただしAPI配送遅延がある状態で不要な30秒レート校正を有効にすると、名目Fsが正しくても測定は数十〜180 ppm程度偏った。変動ゼロ埋めでは全件復号するものの周波数中央値−4.6 Hz。実取得 Fs が確定している場合は不要な到着レート校正をかけない。真のFsが不明なら、配送の揺れを含む短期推定の精度も別に評価する。

## 実 GUI による確認

1.024 MS/sの6サーバを同時に起動し、修正済み macOS Tauri GUI のフロントエンドから自動接続。waterfall・early decode・SQLite記録を有効、PSK Reporterは無効。210秒走らせ、全サーバ共通の7完全スロットを評価。信号源はUTCスロットごとにCQの呼出符号を変える。

別スレッドの取得器がサンプル末尾時刻まで待ってからIQを生成し、API/配送FIFOへ投入する。FIFOの停止中も取得時刻は進む。各ブロックに `first_sample` / `end_sample_exclusive` / 取得UTC / 実配送UTC / 欠落数 / payload数を正解ログとして残し、デコーダには渡さない。未来のサンプル送出がないことをassertし、正解ログにも取得と配送を分離して保存した。

| GUI 条件（−18 dB） | 復号 | 時刻・周波数も正しい | 結果 |
|---|---:|---:|---|
| 取得Fs公称・65 ms削除・750 ms遅延補償・校正有効 | 3/7 | 0/7 | 周波数誤差 -933〜-930 Hz、最大 abs(DT) 50 ms |
| 同じ欠落をゼロ埋め・公称Fs・遅延補償 | 7/7 | 7/7 | 周波数誤差 +0〜+1 Hz、最大 abs(DT) 10 ms |
| 真のFs−1.7%・ゼロ埋め・遅延補償・Fs未補正 | 0/7 | 0/7 | 復号なし |
| 同、ゼロ埋め後にFs校正 | 7/7 | 7/7 | 周波数誤差 -1〜+0 Hz、最大 abs(DT) 15 ms |
| 固定遅延3秒・未補償 | 0/7 | 0/7 | 復号なし |
| 固定遅延3秒・補償 | 7/7 | 7/7 | 周波数誤差 +0〜+1 Hz、最大 abs(DT) 10 ms |

全サーバでdecoderキュー落ち0。報告SNRは−18〜−19 dB。指定1,024,000 S/sに対し、欠落削除サーバのpayloadは評価区間平均988,501 S/s、ゼロ埋めは1,024,000 S/s。真のFsが低いサーバは1,006,592 S/s、ゼロ埋め後のGUIの初期計画レートは1,006,550 S/sだった。実配送遅延は固定750 msのケースで最小約751 ms、API停止時は最大約846 ms。3秒ケースは最小約3001 ms。


さらに別の210秒実行で、取得Fsを公称どおりに固定し、欠落を10秒ごとに19.5 / 65 / 110.5 msへ変動させた。共通の7スロット、−18 dBで次の結果になった。

| 変動欠落の GUI 条件 | 復号 | 時刻・周波数も正しい | 結果 |
|---|---:|---:|---|
| 削除＋平均到着レート補正 | 1/7 | 0/7 | 周波数誤差 -1062〜-1062 Hz、最大 abs(DT) 95 ms |
| ゼロ埋め＋公称Fs | 7/7 | 7/7 | 周波数誤差 -1〜+0 Hz、最大 abs(DT) 15 ms |

削除側の初期GUIレートは982,600 S/s、評価区間payload平均は986,092 S/s。実取得Fsは1,024,000 S/sで一定だった。測定する区間で異なる「実データレート」に引きずられ、唯一の復号も−1062 Hz・DT +95 msとなった。ゼロ埋め側は7/7件、誤差最大1 Hz・15 ms。両条件ともdecoderキュー落ち0。API停止を含む実配送遅延は約751〜892 msだった。

## 実機での対策と確認順

1. **取得レート差と欠落を分離して測る。** 指定Fs、SDKの実Fs通知、各callbackの `firstSampleNum` / 長さ / reset / fsChanged / 到着UTC、TCP送出数を記録する。受信バイト数の傾きだけでは分離できない。
2. **APIの欠落そのものを減らす。** callback内の処理・コピー・ロックを短くし、取得とTCP送出を分けてリングバッファへ渡す。既存dbg4のBULK転送や優先度変更は、その前後でsource counterの穴が減ったかを測る。受信側の見かけレートが上がっただけでは十分ではない。
3. **残った欠落位置を維持する。** SDK counterが欠落を数える場合、`nextFirst − previousEnd` 分のゼロIQを、その位置に挿入する。resetやFs変更は別の不連続として扱う。counterが穴を示さない場合、到着遅延から正確なゼロ埋め位置は決められない。
4. **真の取得Fsが公称どおりならGUIのレート校正を無効にする。** ゼロ埋め後も真のFs差が残るなら、その差だけを補正する。取得counterを含む測定や安定した基準を優先する。ゼロ埋め前の平均配送レートをADCのFsとして固定しない。
5. **固定パイプライン遅延を別に補償する。** GUIの `networkDelayMs` に取得から配送までの固定成分を入れる。可変ジッタは一律のFs変更に変換しない。
6. **後送可能なサーバでは、到着間隔だけの `gap()` 推定を切り離す。** 現行の校正有効/無効と同じスイッチでは、真のFs差の補正と配送停止の誤認を独立に制御できない。counter/取得timestampで本当の欠落を判断する経路が必要。本報告の測定は変更前。その後のGUI組み込みで、到着時刻の最小値を使う設定とgap推定をレート校正から独立させ、gap推定は既定で無効にした。

優先順位は、**欠落発生の抑制 → 残る欠落の位置保持 → 真のFs差の補正 → 固定遅延の補償**。デコーダの探索範囲や閾値を緩める方式は、時間圧縮・位相ジャンプ・間違った周波数変換を直さず、誤ったUTCで復号した結果も成功と扱ってしまう。

## 限界

- 実SDRplayのAPIや以前失敗した録音は使用していない。真のFs差が存在するか、SDK counterが欠落を数えるかは実機ログが必要。実機の症状の原因を断定していない。
- 単一局、固定音声1500 Hz、Gaussian雑音、既知の欠落・配送パターン。混信、周波数ドリフト、マルチパス、フェージング、Fs変更・デバイス再起動は別の試験になる。
- 取得UTCとデコーダUTCの基準時計は一致。時計間のオフセットやドリフトは加えていない。固定遅延補償量と診断用真のFsは既知。
- 仮想時刻試験は192 kS/s、GUIは1.024 MS/s。両者を同じ試行母数に混ぜていない。
- 18/18はこの試験での回収数であり、一般的な感度や長時間の成功確率を保証しない。
