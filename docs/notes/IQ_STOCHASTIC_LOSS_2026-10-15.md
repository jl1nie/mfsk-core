# 確率的な API 欠落と時刻アンカー（2026-10-15）

## 結果

欠落位置を維持するゼロ埋めは、発生時刻・長さがランダムでも有効だった。ただし秒単位の配送停止では、ゼロ埋めに加えて時刻アンカーの扱いを変える必要がある。平均到着レートの補正だけでは安定しない。

SNR −18 dB、各条件20系列×6送信。各欄は「復号数 / UTC・周波数・DTも正しい数」、分母120。後者は発生スロットUTC一致、周波数誤差≤2 Hz、abs(DT)≤50 ms。

| 欠落長の分布 | 削除・公称Fs | 削除・到着レート校正 | ゼロ埋め・公称Fs | ゼロ埋め・最小到着時刻アンカー |
|---|---:|---:|---:|---:|
| 10〜120 ms の一様分布 | 6 / 0 | 4 / 0 | 120 / 114 | 120 / 114 |
| 90%は10〜40 ms、10%は200〜650 ms | 21 / 1 | 8 / 0 | 120 / 120 | 120 / 120 |
| まれに1〜4秒の一様分布 | 91 / 91 | 69 / 58 | 95 / 41 | 118 / 118 |

欠落なしの対照は120 / 120。全260実行で復号workerのキュー落ちは0。[全条件CSV](IQ_STOCHASTIC_LOSS_2026-10-15.csv)。

**表はGUI組み込み前の診断結果。** 真のFsを既知の公称値に固定し、既存の最小到着時刻経路を使い、配送レートtrackerと到着間隔によるgap推定を無効にした。今回この組合せを `rtlMinimumArrival=true` / `rtlInferGaps=false` としてGUIに組み込んだ。確率的条件での実GUI試験と実SDR評価は未実施。GUI組み込み後の設定経路で3分布×20系列＝60実行を再試験し、復号・UTC・DT・周波数・SNRが診断結果と一致した。

## 健全性と条件

[周期的・変動欠落の試験](IQ_TRANSPORT_SIMULATION_2026-10-15.md)と同じ実skimmer receiver / stream / decoderを使用。192 kS/s、信号1500 Hz、IQ中心からダイヤルまで25 kHz、Gaussian雑音。取得UTCと配送UTCを独立に扱い、配送は取得より前に出ない。仮想時刻なのでOS・実APIの挙動そのものは再現しない。

欠落開始までの正常区間は指数分布、欠落長は上表の分布。欠落終了後に次の正常区間を引く交互更新過程で、欠落同士は重ならない。平均欠落率を長期的に3.5%とする正常区間平均を設定した。150秒の信号源は正常状態で開始し、共通評価区間は45〜135秒。実現した評価区間の平均欠落率は順に3.52%、3.45%、3.88%。特にまれな長い欠落では系列ごとのばらつきが大きい。

APIの配送停止は欠落終了＋25 msまで。取得は配送停止中も進む。各系列の同じ欠落位置・同じ雑音を4方式へ与えた。20系列は独立に生成したが、各系列内の6スロットと方式間の結果は相関する。120を独立Bernoulli試行とみなす成功確率や、実機への保証は提示しない。分布は実測SDRログから推定したものではない。

ゼロ埋めは取得側のサンプルカウンタから欠落位置・長さを正確に知る前提。到着間隔から推測したゼロ埋めの試験ではない。配送されるサンプルには信号源UTCを付与していない。固定時計オフセット、真のFs差、混信、フェージングはこの追加試験に含めない。

到着レート校正は30秒を読み捨て、実際のRateMeter、計画レート、tracker、gap推定を使用する。通常実装と同じ±15%の初期レート受理条件も適用した。公称Fs条件は `rtl_calibrate = 0` を明示。以前の診断で既定校正値が残っていた比較を修正し、周期試験330実行と確率試験260実行を再検証した。受理条件の補正が影響する長欠落の1セルも再試験した。

## なぜ長い欠落ではアンカー対策も要るか

ゼロ埋め後も、現在の公称Fs経路は到着時刻の大きな揺れに反応してアンカーを変更する。1〜4秒欠落の20系列では123回のreanchor、復号95/120、厳密な時刻・周波数一致41/120だった。

最小到着時刻アンカーを独立に使用するとreanchorは0、復号118/120、時刻・周波数一致も118/120になった。遅れて配送された区間をサンプル時計の変化と解釈しないことに効果がある。回収できない2送信も残った。波形情報自体が消えるため、時刻を整えるだけで全件を保証できない。

短い一様欠落では全120件復号したが、6件はDTが50 msを超え、最大95 msだった。初期到着の遅れが残る場合があり、最小到着方式だけでも厳密な初期同期を保証しない。

## 大きなずれには Costas による粗い同期取得

ユーザーの指摘どおり、未知の大きな初期ずれ・再接続には信号からスロット位相を推定する段階が必要。方針は次のとおり。

1. サンプル位置を保って音声を広めに保持する。既存 `ft8::acquire::acquire_slot_phase` は25秒の音声に0 / 5 / 10秒の複数窓でCostas探索を行い、15秒周期の位相を循環推定するため、再利用候補になる。
2. 候補の集中度、複数の周波数・送信での一致、可能なら復号確認と後続スロットでの再現を確認してアンカーを修正する。単一の最強候補だけを採用しない。
3. 同期取得後は狭い探索・小さな追従へ移る。配送停止だけでは同期をリセットせず、取得カウンタのresetや真の不連続を別に扱う。

Costasの実装は今回のPRに含めず、GUIでの取得・配送時刻管理を実機評価した後の手段とする。

既存 `bootstrap_dt_median` の上位5候補中央値は±1秒程度の窓向け。広い窓では強い信号の偽ピークに引きずられる既知の制限があるため、大きなずれへそのまま拡張しない。`mfsk-core/tests/ft8_cold_acquisition.rs` と `ft8_coarse_sync_bootstrap.rs` に既存の比較試験がある。

Costasが示すのは信号内の同期位置と15秒周期の位相。15秒の整数倍のUTCずれや、送信局自身の時計ずれと受信パイプライン遅延の分離には、外部UTC・取得timestamp・既知遅延などの対応付けが必要。今回の確率試験にはこのCostasによるアンカー修正を追加していない。

実装上は、**欠落位置の維持、真のFs、配送時刻アンカー、Costasによる初期同期取得を独立に制御する**。これらを一つの「レート校正」スイッチへまとめると、秒単位の配送停止や再接続を正しく扱いにくい。
