# mfsk-serve — マニュアル

`mfsk-core` でデコードとエンコードを行う常駐プロセスです。stdin に 1 行 1 JSON を渡すと、リクエストごとに 1 行以上の JSON が stdout に返ります。

> **サンプルアプリです。** `publish = false` で、独自のタグはありません。他の言語のプログラムから、スロットをまたいでデコーダを保持する使い方を示すために書かれました。
> 読み書きするのはファイルと stdin/stdout だけで、ネットワークも認証もありません。

## 1. なぜ常駐プロセスか

1 スロットずつデコードするプログラムは、スロットごとにプロセスを起動するか、1 つを保持するかを選べます。`Decoder` は呼び出しの間に状態を持ちます:
コールサインのハッシュ表、直近 2 周期(FT8 a7)、周期内のチェックポイント状態です。スロットごとにプロセスを起動すると、毎スロットこれらが空から始まり、
1 スロット前に全文で聞いたコールサインも `<...>` と表示されます。このプロセスは、動いている間、モードごとに 1 つのデコーダを保持します。

これだけで速くなるわけではありません。x86 での実測(`qso3_busy.wav`、1 スレッド)では、ウォームなプロセスが節約するのは、82〜620 ms の呼び出しのうち 10〜21 ms です
(`Depth::Fast` 82 ms、`Normal` 280 ms、`Deep` 620 ms)。ボード上のコストは [#761](https://github.com/jl1nie/mfsk-core/issues/761) の課題で、`bench`(5 節)で測ります。

## 2. インストール

```sh
cargo install --git https://github.com/jl1nie/mfsk-core --rev <commit> --profile dist mfsk-serve
```

`--profile dist` は、fat LTO・コード生成単位 1 のリリースビルドです。Apple の arm64 コアで測ると、どの depth でも 3.6〜5 % 速く、出力は同じで、ビルドは遅くなります(そのマシンで 50 秒、通常は 14 秒)。Raspberry Pi では測っていません。fat LTO のリンクはメモリと時間を多く使うので、1 GB のボードでは終わらないことがあります。失敗したら `--profile dist` を付けずに(通常の `release` プロファイルで)インストールしてください。

`--rev` でビルドを固定します。指定しないと `main` の先端がビルドされ、まだリリースに入っていない変更を含むことがあります。Raspberry Pi では、64 ビット OS を使い、
ボード上でビルドしてください。32 ビット ARM では、rustc 1.100.0 は NEON を不安定なターゲット機能としてしか提供しません(将来エラーになるという警告が出ます)。
`RUSTFLAGS="-C target-cpu=native"` は使えますが、その効果は測っていません。

## 3. コマンド

```text
mfsk-serve                                    stdin が閉じるまでリクエストを処理する
mfsk-serve decode FILE [--mode M] [--depth D] [--band LO-HI]    1 リクエストを処理し、stdout に答える
mfsk-serve bench FILE [--mode M] [--iters N]                    FILE でデコーダの時間を測る
```

どのコマンドも `--threads N`（または環境変数 `MFSK_SERVE_THREADS=N`）で、デコーダのワーカースレッド数に上限をかけられます。`0` または省略なら rayon の既定（全コア、または `RAYON_NUM_THREADS`）のままです。無線機の制御など他のプロセスが同じボードで動くときは指定してください。デコーダは候補ごとの並列処理と `refine_dt` の 3 回の試行で他のコアを使いますが、`--threads 1` なら 1 コアに収まります（出力は同じで、時間だけが変わります）。

`FILE` は `.wav`(モノラル、12 kHz、s16 または f32)か `.raw`(s16le、モノラル、12 kHz)です。`M` はライブラリでの綴りのモード名(`FT8`、`FT4`、
`FST4-60`、`WSPR` など)で、既定は `FT8` です。

## 4. プロトコル

どの行も 1 つの JSON オブジェクトです。リクエストは `op` を持ち、`id` を持つことができます。それに答える行はすべて同じ `id`(任意の JSON 値、または無し)を持ちます。
リクエストは 1 つずつ順に処理されます。処理できない行には `error` が 1 行返り、次のリクエストは通常どおり処理されます。

### `decode`

| フィールド | | |
|---|---|---|
| `mode` | 必須 | モード名 |
| `wav` | 必須 | パス。`.raw` は s16le として、それ以外は WAV として読む |
| `depth` | | `fast`、`normal`、`deep`(無ければライブラリの既定の `deep`) |
| `band` | | `[lo, hi]`(Hz)(無ければそのモードの既定の帯域) |
| `period` | | UTC グリッド上の周期の番号。`prefix` に必要で、周期をまたぐ状態は、これが与えられたときだけ使われる |
| `budget_ms` | | この時間(ミリ秒)が過ぎたら、候補を取るのをやめる |
| `learn` | | デコードの前に `learn_callsign` に渡すコールサイン |
| `prefix` | | `true`: 呼び出しは `Decoder::decode_prefix`、`wav` はそれまでの周期。`period` が必要 |
| `samples` | | ファイルの先頭からこのサンプル数だけを使う。録音全体をチェックポイントごとに再生できる |

depth、帯域などの設定はこのリクエストのものです。省略したリクエストは、前のリクエストの値ではなく既定値になります。

応答: デコードしたメッセージごとに `row` が 1 行、最後に `done` が 1 行です。

```json
{"id":7,"type":"row","mode":"FT8","text":"CQ EA2BFM IN83","freq_hz":2279.75,"dt_sec":0.105,"snr_db":-16.5}
{"id":7,"type":"done","rows":21,"candidates":161,"elapsed_ms":312.9,
 "budget":{"exhausted":false,"candidates_skipped":0,"stages_run":643,"cut_at_sync":null}}
```

`candidates` は、その呼び出しの最初の探索が残した候補の数です(`SlotResult::candidates`。探索した数であり、再現率の指標ではありません)。`budget` はライブラリの
`BudgetReport` です。`elapsed_ms` は壁時計の時間で、人が読むためのものです。

**チェックポイント。** `prefix` を付けると、チェックポイントより前の呼び出しは行を返しません。FT8 のチェックポイントは 141 696、162 432、180 000 サンプルで、
デコーダが自分の一覧を持っています(`AnyDecoder::prefix_points`)。全長での呼び出しは、その周期の完全な集合、つまり周期全体を 1 回で処理した呼び出しと同じ行を、
同じ順序で返します。同じ周期の前の呼び出しで見つかった行も、もう一度含まれます。

### `encode`

| フィールド | | |
|---|---|---|
| `mode`、`text` | 必須 | メッセージ |
| `f0_hz` | 必須 | キャリア: トーン 0 の周波数 |
| `rate` | 必須 | サンプルレート。1〜192 000 Hz |
| `out` | 必須 | パス。s16le の生サンプルがここに書かれる |
| `amplitude` | | s16 波形のピーク(無ければ 14 000) |

```json
{"id":"tx","type":"encoded","mode":"FT8","text":"CQ JA1ABC PM95","hashed_calls":["JA1ABC"],"samples":606720,"out":"/tmp/tx.raw"}
```

`text` は、受信側が表示するとおりのメッセージです。波形は 0 サンプル目から始まる 1 フレームで、周期の中に置く(FT8 では境界の 0.5 秒後)のは呼び出し側の仕事です。
`hashed_calls` は、メッセージがハッシュとして送るコールサインです。プロセスはこれを自分のデコーダに渡す(`learn_callsign`、WSJT-X の `record_tx_hashes`)ので、
それを指す返信が解決されます。

### `error`

```json
{"id":4,"type":"error","error":"unknown depth \"warp\" (fast, normal, deep)"}
```

JSON でない行には `id` がありません。ライブラリの中で panic したリクエストには `error` が返り、そのモードのデコーダは破棄されます(次のリクエストで空のまま作り直されます)。
panic の後は状態が分からないためです。

## 5. ボードで測る

```sh
mfsk-serve bench qso3_busy.wav --iters 6
```

depth ごとに、`whole #i` は周期全体の呼び出しで、`#0` がコールド(プロセスの最初の呼び出しで、スロットごとにプロセスを起動する場合に毎スロット払うもの)です。
続く `prefix period i` は、同じ周期をデコーダのチェックポイントごとに 1 回ずつ流し込んだものです。数値は、実行したマシンの壁時計の時間です。

返信に必要なのは、周期が終わってからの時間です。返信の期限は送信音声の開始で、FT8 では境界の 0.5 秒後です。`decode_prefix` では、その行の最後の数値が該当します。
`Fast` で周期全体を 1 回で処理する場合は、その全体です。ボード上で実行して、これを 0.5 秒と比べてください。呼び出しの時間が段階ごとにどこへ行くか、その読み方は [`docs/notes/FT8_SLOT_PROFILE.md`](../notes/FT8_SLOT_PROFILE.md) にあります。それより前のチェックポイントには、次のチェックポイントまでの時間があります
(FT8 では A から B まで 1.7 秒、B から終了まで 1.5 秒)。

## 6. 制限

- 12 kHz の音声のみです。別のレートのファイルは、リサンプルされずに拒否されます。
- 同時に処理するリクエストは 1 つです。デコーダはプロセス間で共有されません。独立した 2 つのストリームが必要なら、プロセスを 2 つ起動してください。
- `period` は呼び出し側が言ったとおりに扱われます。このプロセスは時計を持ちません。
